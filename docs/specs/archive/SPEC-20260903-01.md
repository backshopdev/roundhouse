# SPEC-20260903-01: GitHub Packages distribution

Last modified: 2026-10-21
Status: Superseded

## Supersession note (2026-10-21)

This specification's distribution approach was superseded by the
package-family migration (DEC-20261017-01..04) — the same charter as its
plan (PLAN-20260903-01, archived): the v0.5.x single-package lifecycle gave
way to the composable package family. The spec's body below stands as the
historical record of the superseded approach.

## Purpose

Define v0.5.0 private npm distribution and the full-template lifecycle for
OpenCode Roundhouse.

## Scope

- Publish `@backshopdev/roundhouse` to GitHub Packages.
- Explicitly deploy the complete packaged `src/` payload with `init` and
  `update` lifecycle commands.
- Report version and paths, remove stale managed workflow files, and support
  dry-run.

Repository development artifacts, credentials, local publishing, and npm
lifecycle deployment are excluded.

## Constraints and quality attributes

- Package version is `0.5.0`; the explicit package allowlist is `package/`,
  `src/`, root `README.md`, and root `LICENSE`, with npm's required
  `package.json` included automatically. Root README and LICENSE are npm
  package metadata; only `src/` is a deployment payload, so root README is
  never copied by `init` or `update`. `src/` includes top-level seed docs,
  consumer-intended `scratch/`, reusable `docs/` index/template artifacts,
  `ktlo/`, `.opencode/`, and `opencode.json`. Root docs, references,
  guiding-principles, and maintenance scripts are excluded. The root
  `.npmignore` is empty and no nested ignore file excludes required `src/`
  content.
- `init` creates missing entries and skips every existing consumer entry.
- `update` overwrites `.opencode/` and `opencode.json`, removes stale managed
  `.opencode/` entries, creates missing seed entries, and never overwrites
  existing seed/template content. No version-specific migration exists yet.
- `.opencode/` is always package-owned in consuming repositories. Consumer
  customization of `.opencode/` is unsupported; users must fork the package
  source to customize it. Consequently, stale entries under `.opencode/` are
  intentionally removed by `update`. Seed/template files outside `.opencode/`
  are create-only after `init`.
- A consumer file occupying the managed `.opencode` root is rejected before
  mutation; the consumer must replace it with a directory before retrying.
- CI publishes only matching `vX.Y.Z` tags with `packages: write`; consumers
  authenticate with GitHub Packages read access (`read:packages`). Forks are
  the customization path.
- Validation runs without package write permission, and publication is a
  separate job that depends on successful validation. The repository must
  manually configure GitHub tag protection or a ruleset for `v*` release tags
  so only authorized maintainers can create, update, or delete them. An
  approved release environment and reviewer may also be manually required
  before publication; these are GitHub settings outside this workflow.
- `--dry-run` performs inspection and reporting without writes.
- Filesystem deployment rejects symlinks/junctions in source trees and in
  destination paths it reads, creates, overwrites, or removes. Mutations
  revalidate paths immediately beforehand. Node
  does not provide one portable no-follow, directory-relative API for all
  recursive operations on supported Windows and POSIX versions, so a malicious
  process racing the final check-and-use can still win; callers should run the
  CLI in a trusted consumer directory.
- The release workflow deliberately uses the broad `v*` trigger. Invalid
  v-prefixed tags schedule and fail strict validation rather than publishing.

```gherkin
@integration

```

## Branch truth rules

- `update` removes stale entries under the package-owned `.opencode/`; `init`
  never removes or overwrites consumer entries. Files outside `.opencode/`
  remain consumer-owned after their initial creation.
- Repository synchronization preserves documented root-only development artifacts.
