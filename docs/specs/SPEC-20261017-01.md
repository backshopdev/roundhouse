# SPEC-20261017-01: Phase 1 migration baseline fixture tooling

## Purpose

Define the expected behavior of the Phase 1 baseline fixture tooling committed
by DEC-20261017-04 Slice A: the committed fixture
`references/migration-baseline.json`, its schema
`references/migration-baseline.schema.json`, the deterministic generator
`scripts/generate-migration-baseline.js`, and the human-authored
`intendedPhase5Owner` ownership annotations. The fixture gives later migration
phases a reproducible baseline of the current `src/` state and the repo-root
leave-alone surface, so drift is detectable against a known state rather than
an opaque "current state" (DEC-20261017-04, Decision drivers). This
specification describes proposed behavior subject to human and review
signoff; `Active` is its document lifecycle status, not evidence that the
fixture tooling is implemented or that any fixture has been generated.

## Scope

### Included

- The fixture format: two scopes in one file (`base: "src"` and
  `base: "root"`), the union vocabulary, per-entry fields, and the canonical
  serialization that makes byte-equality checks meaningful.
- The schema file as the machine-checkable authority for the fixture format.
- The generator's behavior: tracked-path enumeration, classification
  detection rules, annotation merging, canonical serialization, pre-write
  validation, exit codes, and stderr reporting.
- The ownership annotation rules: human authorship, carry-forward on
  regeneration, the pending marker for new managed paths, and loud dropping
  of stale annotations.

### Excluded

- Phase 1 implementation: first execution of the generator against the real
  tree, the test-gap fill (DEC-20261017-04 Slice B), and the baseline summary
  document (Slice C). That work is planned against this specification.
- Characterization adequacy. This specification defines no "adequately
  characterized" quality bar and no test-sufficiency criterion; what counts
  as sufficiently characterized is decided by Phase 1 implementation
  planning, not by fixture tooling.
- The target-state architecture: package contract behavior, composer and CLI
  behavior, and Phase 2+ workspace scaffolding. That specification precedes
  Phase 2/3 planning.
- Changes to sync or deploy behavior. The fixture characterizes current
  behavior; it does not specify changes to `scripts/sync-roundhouse.js` or
  `package/deploy-roundhouse.js`.

### Dependencies

- DEC-20261017-01: Parent decision — composable package architecture; the
  migration context the baseline serves.
- DEC-20261017-02: Package contract — the `@backshop/roundhouse-*` package
  inventory from which `intendedPhase5Owner` values are hand-mapped.
- DEC-20261017-03: Migration strategy — phase ordering; the
  `TODO: <rationale>` convention for ambiguous annotations; the
  generated-permissions-drift risk the baseline mitigates.
- DEC-20261017-04: Phase 1 commitments — Slice A defines the fixture shape
  and is the primary normative source for this specification.
- DEC-20260906-01: Byte-exact commit philosophy — repo precedent for
  byte-level determinism requirements.
- Current-behavior ground truth: `scripts/sync-roundhouse.js` and
  `package/deploy-roundhouse.js`. The detection rules in this specification
  mirror the sync tool's actual Mode 1 / Mode 2 semantics; they do not
  redefine them.

## Terminology

| Term | Meaning |
| --- | --- |
| Baseline fixture | `references/migration-baseline.json`: the committed inventory of tracked source paths under `src/` and tracked root paths with no `src/` counterpart — excluding the fixture file itself — with their classifications, hashes, sizes, and (for managed entries) ownership annotations. |
| Tracked path | A path listed by `git ls-files`. Ignore patterns do not exclude tracked files; untracked paths are never inventoried. |
| Source scope | Fixture entries with `base: "src"`: tracked paths under `src/`. |
| Root scope | Fixture entries with `base: "root"`: tracked paths outside `src/` that the sync or compose tooling leaves alone. |
| Base | Which tree location an entry describes: `"src"` (under `src/`) or `"root"` (repo root outside `src/`). |
| Classification | The union vocabulary: `managed`, `seed`, or `root-only-artifact`. |
| Managed | A Mode 1 overwrite target: tracked paths under `src/.opencode/` plus `src/opencode.json`. Sync always overwrites the root copy and removes stale root entries. |
| Seed | A Mode 2 create-if-missing template: every other tracked path under `src/`. Once copied to root, the root copy is consumer-owned and never overwritten. |
| Seed instance | The root copy of a seed template, created by Mode 2. Derived state, reproducible from the template; not inventoried by the fixture. |
| Root-only artifact | A tracked path outside `src/` with no `src/` counterpart. Sync and the future composer leave it alone entirely. |
| `intendedPhase5Owner` | Human-authored annotation on managed entries naming the `@backshop/roundhouse-*` package that will own the path after the Phase 5 atomic cutover. Informational until Phase 5 enforces it. |
| Stale managed file | A root `.opencode/` entry with no `src/` counterpart. Sync removes it, except entries preserved by the deploy tool's `ROOT_ONLY` list. |
| Stale annotation | An `intendedPhase5Owner` value carried in the existing fixture whose path is absent from the freshly generated inventory or no longer classified managed. |
| Generator | `scripts/generate-migration-baseline.js`: the deterministic source of truth for the fixture's inventory. |
| Idempotent regeneration | Rerunning the generator against an unchanged tree with unchanged annotations produces byte-identical output. |

## Constraints

- **Encoding and line endings.** The fixture and the schema file are UTF-8
  without BOM, with LF line endings only and a single trailing newline.
  Rationale: byte-equality and idempotency checks are only meaningful when
  the bytes are pinned; the repo's byte-exact philosophy is established
  practice (DEC-20260906-01), and CRLF normalization warnings were observed
  on a Windows checkout during the decision-record arc that produced
  DEC-20261017-01 through -04.
- **Checkout-side byte pin.** The fixture tooling deliverables include a
  `.gitattributes` entry pinning LF for the fixture and the schema (for
  example `references/migration-baseline.json text eol=lf` and the
  equivalent for `references/migration-baseline.schema.json`), so
  working-tree bytes equal blob bytes under any checkout configuration.
  Adding that entry is Phase 1 implementation work, not part of this
  documentation changeset; this specification requires it as a deliverable.
  Byte-equality comparisons in SCEN-026 and SCEN-039 are against the
  working-tree file and are made meaningful by this pin.
- **Paths.** Entry paths are repo-root-relative POSIX-style paths (forward
  slashes, no drive letters, no backslashes), sorted ascending by byte-wise
  (code-unit) string order. Paths are globally unique across both scopes.
- **Vocabulary applicability.** `managed` and `seed` apply only to
  `base: "src"`; `root-only-artifact` applies only to `base: "root"`. Any
  other combination is invalid and must fail validation; combination
  validity is owned by the schema layer (Public contracts, Schema file).
- **Annotation integrity.** The generator must not synthesize, guess, or
  alter `intendedPhase5Owner` values. Annotations are human-authored,
  carried forward verbatim on regeneration; new managed paths receive a
  deterministic pending marker; vanished or reclassified annotated paths
  are dropped loudly (Public contracts, annotation merge).
- **Tracked-path enumeration.** The generator inventories git-tracked paths
  only. This makes classification immune to ignore-pattern interactions:
  `src/scratch/README.md` is tracked (un-ignored via `!src/scratch/README.md`,
  commit `c2cb1b2`) and is inventoried despite the `**/scratch/*` ignore
  patterns, while root `scratch/README.md` is untracked and is not.
- **No environment-dependent content.** The fixture contains no timestamps,
  host data, tool versions, or commit references. Anything that varies
  between machines or moments breaks byte-equality.
- **Runtime.** Node 24 with built-in modules only (`node:fs`, `node:path`,
  `node:crypto`, `node:child_process`); no new dependencies, matching the
  `scripts/commit.js` precedent.
- **Fail-closed writes.** On an unclassifiable tracked path, a tracked
  symlink, a tracked path missing on disk, a validation failure, or an
  invalid existing fixture (unparseable, schema-invalid, structurally
  invalid — duplicate or unsorted paths — or carrying a misplaced
  annotation), the generator writes nothing.
- **Specification boundary.** This specification defines fixture tooling
  only. It defines no characterization adequacy bar and no target-state
  architecture behavior.

## Quality attributes

- **Determinism:** Regeneration against an unchanged tree with unchanged
  annotations is byte-identical in 100% of runs; assertable by test.
- **Performance:** A full generation run completes within 5 seconds on the
  current repository (several hundred tracked files).
- **Integrity:** Every entry's `sha256` and `sizeBytes` match the file
  content at generation time; verifiable by test against the current tree.
- **Portability:** Byte-equality holds across Windows and POSIX checkouts:
  LF-only, no BOM, POSIX separators, no platform-dependent ordering.
- **Reliability:** Exit codes distinguish success (0), failure (1), and
  usage error (2). Every dropped annotation and every untracked-path
  warning is listed on stderr; there are zero silent mutations.
- **Security:** The generator performs no network access, writes exactly
  one target file (`references/migration-baseline.json`), and handles no
  secrets; it reads only repository-tracked content and the existing
  fixture file.
- **Inspectability:** The committed fixture is human-readable, two-space
  indented JSON with pinned member order, so annotation and inventory
  changes are reviewable as ordinary diffs.

## Public contracts

These contracts are defined inline in this specification; no
`docs/contracts/` file is created. Rationale: the house contract template is
HTTP-API-shaped (authentication, endpoints, error semantics) and does not
map to a file format plus script behavior; the machine-checkable authority
for the fixture format is the schema file itself once Phase 1 implements it;
and house precedent (SPEC-20261016-01) accepts inline contracts with stated
rationale. If a future consumer needs a standalone contract document, one
can be split out at that point.

### Fixture JSON format

The fixture is a JSON object with exactly two top-level members, in this
order:

- `schemaVersion` — integer, currently `1`.
- `entries` — array of entry objects, sorted ascending byte-wise by `path`.

Each entry is an object with members in this order:

- `path` — string; repo-root-relative POSIX path.
- `base` — `"src"` or `"root"`.
- `classification` — `managed`, `seed`, or `root-only-artifact`.
- `sha256` — string; 64 lowercase hexadecimal characters; SHA-256 of the
  file content at generation time.
- `sizeBytes` — integer, zero or greater; file size in bytes at generation
  time.
- `intendedPhase5Owner` — string; present if and only if `classification`
  is `managed`. Seed and root-only-artifact entries must not carry it.

`src/opencode.json` is a managed entry like any other; DEC-20261017-04's
explicit callout of its SHA-256 and byte size is an instance of the general
per-entry rule, not a special field. The fixture inventories files, not
directories; tracked paths are files.

Serialization canon: UTF-8 without BOM; LF line endings; two-space
indentation; the member orders above; a single trailing newline.

### Schema file

`references/migration-baseline.schema.json` is a JSON Schema (Draft
2020-12) document that encodes the fixture format above, including the
conditional requirements: `base: "src"` with `classification: "managed"`
requires `intendedPhase5Owner`; `classification: "seed"` or
`"root-only-artifact"` forbids it; `base: "root"` requires
`classification: "root-only-artifact"`; enum, pattern, and numeric
constraints per the field definitions above. The schema layer owns
base/classification combination validity; the generator's own checks cover
only what JSON Schema cannot express — path uniqueness and sort order. The
schema is committed and is the machine-checkable authority for the fixture
format.

### Generator behavior

Invocation: `node scripts/generate-migration-baseline.js`. The generator
accepts no arguments: any argument at all is a usage error — exit 2 with
usage text on stderr, mirroring `scripts/sync-roundhouse.js`'s strict
argument parsing. The generator:

1. Enumerates tracked paths via `git ls-files`.
2. Classifies every tracked path (detection rules below) and computes
   `sha256` and `sizeBytes` from file content; a tracked symlink or a
   tracked path missing on disk fails here (outcomes below).
3. Validates the existing fixture file at `references/migration-baseline.json`
   in the working tree: it must parse, conform to the schema, and carry no
   misplaced annotation (input validation; outcomes below).
4. Merges annotations from the validated existing fixture (annotation merge
   below).
5. Serializes canonically and validates the output: against the schema
   file, which owns base/classification combination validity, plus its own
   checks for path uniqueness and sort order.
6. Writes `references/migration-baseline.json`.

Detection rules, total over tracked paths:

- The fixture file itself (`references/migration-baseline.json`) is never
  inventoried. Rationale: a self-referential entry would require the file's
  hash to appear inside the hashed content — no fixed point exists — and
  manifest tools conventionally exclude their own output.
- A tracked path under `src/`: `base: "src"`; `classification: "managed"`
  if the path is under `src/.opencode/` or is `src/opencode.json`;
  otherwise `classification: "seed"`. This mirrors sync Mode 1 (overwrite)
  and Mode 2 (create-if-missing) exactly.
- A tracked path outside `src/`: if `src/<path>` exists, the root path is a
  seed instance — derived state, not inventoried. Otherwise:
  `base: "root"`, `classification: "root-only-artifact"`. This captures the
  current leave-alone surface: `package.json`, `LICENSE`,
  `guiding-principles.md`, `.github/`, `references/`, `scripts/`,
  `package/`, `.gitignore`, `.markdownlint-cli2.jsonc`, `.npmignore`, and
  any later path with no `src/` counterpart. The seed-instance exclusion is
  contingent on open question 2; if that reconciliation is not confirmed,
  this rule and SCEN-029 must be revisited.
- A tracked symlink is rejected: exit 1, no write, path listed on stderr.
  This matches the repo's existing symlink/junction rejection posture.
- Every tracked path must classify. An unclassifiable tracked path indicates
  a generator defect or an unanticipated repo shape: exit 1, no write.

Outcomes:

- Invalid existing fixture (input validation): unparseable, schema-invalid,
  structurally invalid, or carrying an `intendedPhase5Owner` on a non-managed
  entry: exit 1, nothing written, the offending path or parse error listed
  on stderr.
- Schema validation failure of the generated output, structural validation
  failure (duplicate or unsorted paths), unclassifiable tracked path,
  tracked symlink, or tracked path missing on disk: exit 1, nothing
  written, the offending path listed on stderr where applicable.
- Stale annotations (annotated path absent from the fresh inventory or no
  longer classified managed): the regenerated fixture is written without
  them, exit 1, each dropped path listed on stderr. The inventory stays
  tree-true and the removal is loud and reviewed, never silent.
- Untracked-and-not-ignored paths present under `src/` or at repo root:
  warning on stderr listing them, exit 0, fixture membership unchanged.
- Any argument supplied: usage error — exit 2, usage text on stderr,
  nothing written.
- Success: exit 0.

The generator does not compare its output against the committed fixture for
drift; drift detection belongs to the Phase 1 tests that assert
regeneration equality and tree match (DEC-20261017-04 Slice A). Stale-managed
detection — root `.opencode/` entries with no `src/` counterpart — remains
sync verify's responsibility (`scripts/sync-roundhouse.js --mode verify`),
not the fixture tooling's.

### Annotation merge

- For each managed path present in both the existing fixture file at
  `references/migration-baseline.json` in the working tree and the fresh
  inventory: the existing `intendedPhase5Owner` value is carried forward
  verbatim. The generator never alters, reorders, or regenerates an
  existing annotation value.
- For a managed path present only in the fresh inventory:
  `intendedPhase5Owner` is the deterministic pending marker
  `TODO: pending human mapping (new path at generation time)`, shaped per
  DEC-20261017-03's `TODO: <rationale>` convention. No package name is ever
  synthesized.
- For an annotated path absent from the fresh inventory or no longer
  classified managed: the annotation is dropped and the outcome is the
  stale-annotation case above.
- The generator validates the existing fixture before merging (Generator
  behavior, step 3). An `intendedPhase5Owner` on a seed or
  root-only-artifact entry in the existing fixture is an input validation
  error in the same failure family as an unparseable fixture: exit 1,
  nothing written, offending path listed on stderr.

## Scenarios

Scenario IDs allocate from SCEN-026: SCEN-001..003 are used by
SPEC-20260903-01 and SCEN-004..025 by SPEC-20261016-01; this specification
allocates SCEN-026..045. docs-check enforces globally unique, non-reused
IDs. Each scenario carries its ID as a Gherkin tag and as a trailing name
suffix, two representations of the same ID per the convention in
SPEC-20261016-01. Scenarios that invoke the generator or inspect the real
repository tree and git are `@integration`; pure transform and validation
logic over in-memory inputs is `@unit`. These are acceptance contracts for
future implementation, not evidence of executed tests.

## Branch truth rules

- Tree and annotations unchanged → byte-identical regeneration, exit 0
  (SCEN-026).
- New managed path → pending-marker annotation, never a guessed owner
  (SCEN-035). Annotated path vanished or no longer classified managed →
  fixture written without it, exit 1, stderr list (SCEN-036). Invalid
  existing fixture (unparseable, schema-invalid, structurally invalid,
  misplaced annotation) →
  no write, exit 1, offending path on stderr (SCEN-037). Unclassifiable
  path, tracked symlink, tracked-but-absent path, structural failure, or
  schema-invalid output → no write, exit 1 (SCEN-032, SCEN-033, SCEN-038,
  SCEN-043, SCEN-044). Untracked-and-not-ignored paths present → stderr
  warning, exit 0, membership unchanged (SCEN-041). Any argument supplied →
  usage error, exit 2, nothing written (SCEN-045).
- Tracked path → dispositioned per the detection rules (inventoried, except
  the fixture file itself) regardless of ignore patterns; untracked path →
  never inventoried (SCEN-030).
- Root path with a `src/` counterpart → seed instance, not inventoried
  (contingent on open question 2); without one → root-only-artifact, except
  the fixture file itself, which is never inventoried (SCEN-029).
- `base: "src"` → `managed` or `seed`; `base: "root"` →
  `root-only-artifact`; any other combination is invalid, owned by the
  schema layer, and fails closed (SCEN-038).
