# SPEC-20261016-01: Human-directed branches and GitHub PR creation

## Purpose

Define optional, human-directed branch selection and pull request (PR)
publication for the Roundhouse workflow, separating provider-neutral Git
behavior from hosting-provider operations. GitHub is the initial supported PR
provider. This specification describes proposed behavior subject to human and
review signoff; `Active` is its document lifecycle status, not evidence that
the capability is implemented or authorized for execution.

## Scope

### Included

- Beginning-of-work branch dialog, including accepting an appropriate existing
  branch or declining a new branch.
- Progressive discovery of consuming repository/team branch-name, PR-title,
  and PR-content conventions through `CONTRIBUTING.md`, with human
  clarification of relevant gaps, ambiguities, conflicts, or proposed departures.
- Optional draft or ready PR creation for the actual human-selected scope,
  including documentation-only work and partial implementation of an already
  approved, committed plan.
- Explicit publication approval, concrete PR content, destination confirmation,
  operation outcomes, and human-directed abandonment without automatic cleanup.
- Inline human/agent workflow contracts; no separate contract file is needed.

### Excluded

- Implementation instructions, command syntax, permission patterns, transport
  selection, or new requirements on branch names or plan metadata.
- Implementing GitLab or Bitbucket PR operations, fork support, PR merging,
  auto-merge, branch protection, or repository-setting changes.
- Automatic PR creation, push, PR closure, branch deletion, or work discard.
- Replacing existing commit, push, review, or implementation-approval gates.
  Approval of this specification alone authorizes none of those operations.

### Dependencies

- Preserve the gates and safeguards in the
  [workflow](../../AGENTIC_WORKFLOW.md) and
  [autonomy model](../../src/.opencode/workflow-docs/autonomy/index.md).
  Existing commit and exact-destination push procedures remain owned by
  [git-commit](../../src/.opencode/skills/git-commit/SKILL.md); this specification
  does not duplicate or replace that procedure.
- When defining behavior, use the
  [specification standard](../../src/.opencode/skills/specification/SKILL.md).
  When recording a decision, use the
  [decision-record standard](../../src/.opencode/skills/decision-record/SKILL.md).
  When planning implementation, use the
  [implementation-plan standard](../../src/.opencode/skills/implementation-plan/SKILL.md).
  When authoring or navigating durable artifacts, use
  [repository documentation](../../src/.opencode/skills/repository-documentation/SKILL.md).
  These are conditional resources, not a mandatory decision → spec → plan chain.

## Terminology

| Term | Meaning |
| --- | --- |
| Selected scope | The work the human agrees this PR should contain; it need not encompass an entire plan or implementation. |
| Publishable committed content | Committed content suitable for the selected PR scope after applicable existing gates; draft content may disclose incomplete work. |
| Branch starting point | The explicitly confirmed repository and base/ref from which a chosen new branch starts. |
| PR destination | The explicitly approved hosting repository and target base branch; distinct from the Git push destination. |
| Source branch | The branch whose published commits are proposed for the PR. |
| Draft / ready | Human-selected PR state: early feedback with incompleteness disclosed, or completed agreed scope respectively. |
| Publication proposal | The complete title, body, destination repository/base, source branch, and draft/ready state presented for approval. |
| Publication field change | Any change to the approved exact title, full body, destination repository, target base, source branch, or draft/ready state, including wording, formatting, or punctuation. |
| Resolved repo conventions | Relevant consuming repository/team guidance discovered through `CONTRIBUTING.md`, directly or through its references, with any gaps, ambiguities in meaning or applicability, conflicts, or departures explicitly clarified with the collaborator. |

## Constraints

- The orchestrator asks at the beginning of work whether the collaborator wants
  a branch and proposes a name using repository/team conventions. The human
  decides. Recognize an appropriate existing branch rather than force a
  duplicate. Impose no new prefix, naming format, ASCII restriction, length
  limit, or plan field.
- Branch naming, PR title style, and PR content conventions belong to the
  consuming repository/team. Use `CONTRIBUTING.md` as the standard discovery
  point; read relevant guidance there and follow relevant references to guides
  or PR templates progressively, not all repository documentation. Missing,
  ambiguous, or contradictory relevant guidance requires collaborator
  clarification before the affected operation. Do not unilaterally choose an
  interpretation or applicable variant, invent precedence, or impose defaults.
- Follow resolved repo conventions when proposing branch names, PR titles,
  and full bodies. Propose departures for explicit human clarification and
  approval rather than silently assuming them. This specification imposes no
  Conventional Commit PR title, body headings, list limit, naming prefix,
  length or ASCII restriction, extra metadata, or required additional document.
- Explicitly confirm a new branch's repository and starting point before
  creation. A chosen branch exists before commits intended for it. There is no
  fixed gate timing or requirement that a plan be authored first. Branch
  consent does not authorize commits or implementation.
- Work can be a decision record, specification, committed plan, implementation
  of some or all tasks of an already approved committed plan, a full
  decision-through-implementation arc, or other approved scope. These examples
  are illustrative, not exclusive. Do not impose an artifact chain or deny
  documentation-only or bugfix PRs for lacking one.
- PR creation is available, not mandatory. At human direction, publishable
  committed content may support a draft for early feedback while more work
  remains. A ready PR represents completed agreed scope, not necessarily all
  tasks of a wider plan. The human chooses draft or ready; do not silently
  promote a draft or treat incomplete whole-plan work as disqualifying it.
- Never assume `main`, `origin`, upstream, or current `HEAD` is the intended
  branch starting point or publication destination. Missing or ambiguous
  repository/base/source choices require confirmation before the affected write.
- Preserve no force-push, no hook bypass, no permission-evasion wrappers, no
  auto-approval, and no persistent `always` approval. Preserve existing commit
  and exact explicit push-destination contracts, including separate chat
  authorization and fresh `once` confirmation for commit/push execution.
- PR creation is a hosting-provider external write, separate from Git push.
  Neither approval authorizes the other; commit approval authorizes neither.
  Technical enforcement must agree with the publication approval boundary.
  Do not promise a `once` prompt for a PR command matched by an `allow` rule;
  command selection and permission configuration remain implementation work.
- Any publication field change requires renewed explicit human approval of the
  complete current proposal before publication, including wording, formatting,
  or punctuation changes. Do not normalize or silently edit approved content.

## Quality attributes

- **Authorization/security:** Every PR creation has explicit prior human
  approval of all six exact publication fields. There are zero publication
  writes after withheld approval or any unapproved publication field change,
  including wording, formatting, or punctuation. Push and cleanup each retain
  their own explicit authority.
- **Destination safety:** Every branch creation and PR creation uses a confirmed
  repository and respective base; every push retains the existing explicit
  remote/source/destination-ref approval contract. Ambiguity causes zero writes
  to the affected destination.
- **Reliability:** Every attempted external operation is reported as verified
  success, established failure/not executed, or unresolved. There are zero
  blind retries and zero automatic cleanup operations after failure,
  uncertainty, or abandonment.
- **Inspectability:** Every proposed title/body follows resolved repo conventions
  and the full body identifies actual selected scope and validation status.
  Every unresolved relevant guidance gap, ambiguity, or conflict produces a clarification
  request and zero affected operations until resolved. Drafts disclose incomplete
  work; unexecuted validation is never claimed as passed. Static walkthroughs
  are not runtime or permission-enforcement proof.
- **Portability:** Branch/commit/push contracts do not require a hosting
  provider's PR CLI. GitHub PR behavior is distinguished from Git behavior;
  unsupported providers receive no attempted PR write.

## Public contracts

### Convention discovery and clarification

For branch naming, PR title style, and PR content conventions, start at the
consuming repository's `CONTRIBUTING.md`. It may provide guidance directly or
reference dedicated guides or PR templates. Load only the references relevant
to the current branch or publication proposal, progressively as needed. Do not
require an extra convention document or read all repository documentation.

If `CONTRIBUTING.md` is absent, relevant guidance is missing or ambiguous, or
relevant instructions contradict each other, ask the collaborator to clarify
before the affected operation. Ambiguity includes present, noncontradictory
guidance with multiple plausible meanings or applicable variants, such as two
PR templates without selection rules or guidance whose applicability is unclear.
Do not unilaterally choose an interpretation or template, substitute a harness
naming/title/body default, or invent instruction precedence. The collaborator may
explicitly clarify conventions or approve a proposed departure; do not assume
such approval. Resolving a convention does not authorize a branch write or PR
publication. The complete exact publication proposal still requires its own
approval, and any later field change still requires renewed complete approval.

### Branch dialog and work selection

The orchestrator presents branch choice and a name proposal using resolved repo
conventions at the beginning of work, asking for clarification where needed.
Accepting, declining, or recognizing an appropriate
existing branch leaves applicable work-approval gates intact. If a new branch
is chosen but its repository or starting point is unknown, the orchestrator
requests confirmation, not a unilateral default. If branch creation fails or
is unclear, commits intended for that branch wait for resolution; no fallback
commit to another branch is authorized.

Selected artifacts and implementation scope govern the work. Consult the
relevant dependency resources only as needed; none is a prerequisite merely
because a PR is contemplated. A committed plan's remaining tasks may stay out
of a PR whose agreed scope is a completed subset.

### Publication proposal and approval

Before PR creation, present the exact proposed title and full body together
with destination repository, target base branch, source branch, and draft/ready
state. Make the actual selected scope and validation evidence inspectable.
Obtain explicit human approval of that exact proposal before publication. An
omitted field, withheld approval, or any change to an approved publication field
blocks creation until the complete current proposal receives explicit approval.
This includes wording, formatting, and punctuation changes, even when meaning
is unchanged; do not normalize approved content. An unchanged approved proposal
may proceed subject to applicable existing gates and technical enforcement.
Commit or push approval is not publication approval. PR approval is not push
approval; any required push still follows its existing separate authorization
procedure.

Propose the actual title and full body using resolved repo conventions, not a
harness title style or universal body template. Repository/team guidance may
require a format; this specification does not supply one when guidance is
missing. A title outside Conventional Commit form is acceptable when consistent
with resolved repo conventions. Proposed departures require explicit human
clarification and approval before the affected operation.

The body describes actual selected scope and validation rather than generic
placeholder text. Validation distinguishes executed checks, static
inspection/walkthroughs, and remaining steps. A draft can explicitly disclose
unfinished work and pending validation without implying completion. These are
inspectability requirements, not prescribed headings or layout.

### Provider boundary, outcomes, and abandonment

Provider-neutral Git branch/commit/push behavior remains separate from GitHub
PR operations. GitHub is the initial supported hosting provider; potential
GitLab/Bitbucket support is future work, not an assumption that all hosting
providers share a CLI. An unsupported or unidentified PR provider blocks the
PR write and prompts clarification without removing independently authorized
Git capabilities.

Report actual operation results, not inferred success. For an unclear push,
retain the existing status-first, read-only verification procedure, including
the exact approved destination and configured push destination when necessary;
do not use `git fetch` as a write probe or expose credentials. For an unclear PR
creation, use read-only evidence scoped to the approved repository/source/base
to determine whether the intended PR exists before considering a retry. A
confirmed success is reported without retry. Established failure, denied
permission, or nonexecution is reported; retry requires renewed explicit human
authorization and applicable technical permission confirmation. An unresolved
result is reported and paused, not guessed or retried. No alternate command or
transport may be used to evade a denial. Authentication prerequisites do not
authorize credential disclosure or repository-setting changes.

The human may abandon work at any point and decides any cleanup. Preserve
unrelated work. Abandonment does not authorize discard, PR closure, or local or
remote branch deletion. Any cleanup requires its own explicitly approved
scope and applicable safeguards. Do not assume a remote branch or PR exists or
require deletion of the currently checked-out branch.

## Scenarios

These are acceptance contracts, not evidence of existing or executed tests.
All scenarios are `@integration`: they evaluate agent interaction with workflow
instructions, conversation state, and tool routing, sometimes also Git or a
hosting interface. Controlled conversations and mocked tools do not make an
LLM-session evaluation a unit test. A deterministic assertion about an output
does not change the whole scenario's classification. A deterministic validator
could have unit tests if separately designed and approved; none is required or
assumed here.

The tags describe intended verification categories, not implementation or test
availability. Static authoring walkthroughs are not executed scenario tests,
runtime evidence, or permission-enforcement proof. Agent evaluations may be
nondeterministic; one passing trace does not establish universal adherence.

Each scenario's stable ID appears as an actual Gherkin tag. The matching ID
suffix in its scenario name is temporarily retained for compatibility with the
current docs-check parser; these are two representations of the same scenario
ID, not separate scenarios or new allocations.

## Scenario-to-verification mapping

The intended methods below identify evidence boundaries, not a mandated test
framework or new infrastructure. They require separate implementation and
execution authority; none was executed during specification authoring.

- **Agent interaction:** Evaluate the orchestrator with controlled conversation
  inputs, relevant instructions, and controlled/mocked tool responses. Record
  the conversation, resource routing, and all attempted tool calls, including
  blocked calls. Assert both required responses and absence of forbidden calls
  over the evaluated interaction. Such a trace shows only the exercised cases,
  not universal adherence, actual tool side effects, or permission enforcement.
- **Local Git integration:** Combine agent interaction with an isolated Git
  fixture when repository state or operation ordering is the assertion. Record
  calls and inspect refs, commits, and worktree state. Mocked Git responses alone
  cannot establish real Git state; a local fixture cannot establish hosting
  behavior or production permission enforcement.
- **GitHub interface integration:** Combine agent interaction with controlled or
  stubbed hosting responses and record requests, read-back results, and reports.
  This tests routing and response handling, not actual GitHub publication,
  authentication, or enforcement. A claim about real provider behavior needs
  separately authorized real-provider execution and read-back evidence; stubbed
  results must never be reported as that evidence.

to implementation planning and its human/review approval; this specification
does not claim current configuration enforces the proposed PR capability.
Future GitLab/Bitbucket behavior requires separate scope and approval.

## Branch truth rules

These are conditional workflow behavior rules, not Git branch-naming rules.

- Branch declined → no new branch; appropriate existing branch recognized → no
  duplicate; new branch chosen → confirmed repository/starting point and branch
  existence before intended commits. Branch failure/uncertainty blocks those
  commits, not permission to move them elsewhere (SCEN-004–SCEN-009).
- Documentation-only, bugfix, selected plan subset, or broader arc → evaluate
  agreed scope and applicable gates, not a mandatory artifact chain. Draft →
  committed early-feedback scope with incompleteness disclosed; ready →
  completed agreed scope; PR declined → no publication (SCEN-010–SCEN-013).
- Complete current proposal approved and unchanged → publication eligible under
  applicable technical enforcement; missing/withheld approval or any publication
  field change, including wording, formatting, or punctuation → no PR write
  until the complete current proposal receives explicit approval. Push approval
  remains independent (SCEN-014–SCEN-019).
- Relevant conventions directly in `CONTRIBUTING.md` → use them; references to
  guides/templates → read progressively as relevant; absent/missing/ambiguous/conflicting
  relevant guidance → ask and pause the affected operation without defaults or
  unilateral interpretation/template choice or invented precedence; explicit human clarification or approved departure →
  use that resolution while retaining independent operation approvals
  (SCEN-004, SCEN-015–SCEN-018).
- GitHub → initial PR support; other/unknown provider → no PR write pending
  separate support or clarification, without redefining Git (SCEN-020).
- Verified success → report, no retry; established failure/nonexecution → report
  and renewed retry authorization; unresolved → read-only checks and pause if
  unresolved. Abandonment → no cleanup absent approved scope
  (SCEN-021–SCEN-025).
