# SPEC-20261019-02: Phase 3 composer

## Purpose

Define the Phase 3 composer: the `@backshop/roundhouse-cli` implementation
that discovers installed Roundhouse packages, validates their contracts, and
renders the consumer's `opencode.json` from a Core-owned template plus the
normalized capability model — together with the `roundhouse.json` vocabulary
it consumes, the `.roundhouse/manifest.json` schema it maintains, the
fixture-package format it is tested against, and the `init` / `compose` /
`verify` command surface. The composed `opencode.json` looks like today's root
file with computed skill allowlists: agent scaffolding and role-driven tool
posture stay Core template content, skill availability is computed uniform,
and bash maps carry two distinguishable layers. Phase 3 builds the composer
against fixture packages only — no real content moves (DEC-20261017-03). This
specification describes proposed behavior subject to human and review signoff;
`Active` is its document lifecycle status, not evidence that the composer is
implemented.

## Scope

### Included

- **The `roundhouse.json` vocabulary.** The concrete capability schema the
  Phase 2 stub envelopes deferred: `kind`, `contractVersion`, `skills`,
  `bash`, `requires` (Public contracts, roundhouse.json vocabulary). The
  vocabulary supersedes the stubs' `capabilities` placeholder member.
- **The rendering model.** Three layers — template scaffolding, computed
  uniform skill maps, and two-layer bash maps — rendered into the consumer's
  `opencode.json` (Public contracts, Rendered opencode.json).
- **The validating renderer.** The Core template's pinned name and location,
  its validation contract, and fail-closed behavior on every invariant
  (Public contracts, Core template).
- **The manifest.** The exact `.roundhouse/manifest.json` schema, its
  canonical serialization, and its committed status (Public contracts,
  Manifest).
- **The fixture-package format.** The checked-in fixture packages under the
  CLI package's test area, their format, and their naming (Public contracts,
  Fixture packages).
- **The CLI public surface.** The `roundhouse` bin, the three commands, exit
  codes 0/1/2 mirroring the fixture generator, and stderr reporting (Public
  contracts, Command semantics).
- **The discovery contract.** Declared dependencies and workspace members;
  never a blind `node_modules` scan. Workspace members are the self-hosting
  concretization of DEC-20261017-01's self-hosting requirement: external
  consumers discover via declared dependencies; the self-hosting root
  discovers via workspace members.
- **The stub-envelope migration.** The 28 Phase 2 stub envelopes carry the
  superseded `capabilities` placeholder; migrating them to the vocabulary
  below is a mechanical empty-collection rename (timing: Open questions).

### Excluded

- **The Phase 5 content migration.** No real content moves. The real Core
  template instantiation — derived from the current root `opencode.json` at
  cutover time — is Phase 5 work: landing it earlier would create a second
  canonical copy of `src/opencode.json` before the atomic cutover retires it.
  This specification pins the template's contract and location; the fixtures
  carry fixture templates.
- **The detailed agent-prompt content.** Phase 4 territory (DEC-20261017-03).
- **The composition matrix.** Phase 7 territory; the fixture format is
  designed for its reuse, but the matrix itself is out of scope.
- **Publishing and CI.** Phase 9 territory.
- **The org-workflow package.** Example-only per DEC-20261017-02; no workflow
  package is scaffolded or composed here.
- **CLI source layout.** The bin entry plus lib modules arrangement is
  plan-level; the public surface is the contract.
- **Package install/remove.** npm's job in v1; the CLI does not wrap
  `npm install` or `npm uninstall` (DEC-20261017-02).

## Terminology

| Term | Meaning |
| --- | --- |
| Composer | The `@backshop/roundhouse-cli` implementation: discovery, validation, rendering, managed/seed materialization, manifest maintenance, and verification. |
| Template | `opencode-template.json` at the core package's root: the Core-owned `opencode.json` shape carrying the shell, agent scaffolding, tool permissions, deny-all wildcards, and role-driven bash maps. Composer input, never copied to the consumer. |
| Rendered `opencode.json` | The composed artifact: the template rendered with computed skill maps and unioned bash maps. Regenerated on every compose. |
| Installed skill | A skill ID declared by a discovered package's `skills` array and present at the managed-path convention location in that package. |
| Uniform skill availability | The ruled model in which every installed skill is loadable by every agent; role boundaries are tool permissions and agent prompts, never skill availability. |
| Skill-driven bash allows | The allow patterns packages declare in `bash`, unioned into all four agents' bash maps by the composer. |
| Role-driven bash allows | The bash-map entries the template itself carries: Core's per-agent role posture. |
| Discovered set | The packages discovery admits: declared dependencies and workspace members exposing a valid `roundhouse.json`. |
| Manifest | `.roundhouse/manifest.json`: the generated composition and ownership record; committed. |
| Stale managed file | A consumer managed file recorded in the manifest that the recomputed composition no longer owns. |
| Missing managed file | A manifest-recorded managed path absent from the consumer tree. |
| Seed offer | A seed path a package offers via its `seed/` tree; created only when absent, never overwritten. |
| Seed instance | The consumer-rooted copy of a seed template. Consumer-editable once created; a deleted instance is recreated by compose (create-if-missing, matching sync Mode 2). |
| Fixture package | A minimal checked-in package under the CLI test area exercising one composer behavior. |

## Constraints

- **Fail-closed composition.** Every validation failure — vocabulary
  violation, duplicate ownership, missing requires, a requires cycle, a
  dependency-rule violation, a bash-pattern collision with a role-driven
  non-allow template entry, template invariant, declared-but-missing or
  present-but-undeclared skill content, a skill frontmatter name that does
  not equal its directory ID, path escape, contract-version
  mismatch — exits 1, reports on stderr, and writes nothing:
  all validation precedes any write.
- **Uniform skill availability.** No per-agent skill availability exists
  anywhere in the vocabulary or the rendering. The manifest vocabulary has no
  availability field; the template's skill maps carry exactly the deny-all
  wildcard; the rendered skill maps are identical across the four agents.
- **Allow-only bash contributions.** Packages declare allow patterns only.
  Deny and ask posture is Core role-driven template content; no package can
  restrict or escalate another agent's bash posture.
- **Agent-path reservation.** Managed paths under `.opencode/agents/` may be
  declared only by the core-kind package; any other package declaring one
  fails composition (DEC-20261017-02).
- **Exactly one core package.** Exactly one discovered package may declare
  `kind: "core"`; it must carry the template at the pinned location. Zero or
  multiple core-kind packages fail composition.
- **Node 24, built-ins only.** The CLI runs on Node 24 with built-in modules
  only; no new dependencies (the `scripts/commit.js` and fixture-generator
  precedent).
- **No network access.** Discovery resolves local package roots; the composer
  performs no network operations and handles no secrets.
- **Path confinement.** Managed and seed paths are consumer-root-relative
  POSIX-style paths confined to their consumer roots (`managed/` materializes
  into `.opencode/`, `seed/` into the consumer root); absolute paths,
  backslashes, and escape traversals are rejected, as are symlinked managed
  or seed sources — the safety primitives ported from
  `package/deploy-roundhouse.js` (DEC-20261017-03's risk table).
- **Canonical serialization.** The manifest and the rendered `opencode.json`
  are UTF-8 without BOM, LF line endings, two-space indentation, pinned member
  order, single trailing newline — byte-stable and reviewable as ordinary
  diffs (DEC-20260906-01 precedent).
- **Committed manifest.** `.roundhouse/manifest.json` is committed so
  composition changes are reviewable (DEC-20261017-02).
- **Exit codes and reporting.** Exit 0 success, 1 failure, 2 usage error,
  mirroring the fixture generator. Every rejection, removal, creation, and
  warning is listed on stderr; there are zero silent mutations.
- **No package-manager wrapping.** The CLI does not wrap `npm install` or
  `npm uninstall`.

## Quality attributes

- **Determinism:** The same discovered set, template, and package content
  produce byte-identical rendered `opencode.json` and manifest; assertable by
  test.
- **Reliability:** Exit codes distinguish success (0), failure (1), and usage
  error (2). Every removed stale file, created seed, and rejected declaration
  is listed on stderr.
- **Security:** No network access; path-escape rejection on every materialized
  path; packages cannot escalate permissions — allow-only bash contributions,
  agent-path reservation, and uniform skill maps remove skill availability as
  a privilege lever.
- **Performance:** A full compose of the Roundhouse repository's 28-package
  set completes within 5 seconds on the current repository scale.
- **Inspectability:** The rendered `opencode.json` and the manifest are
  two-space-indented JSON with pinned member order; the two bash layers are
  distinguishable in the rendered output and verifiable from package
  declarations.

## Public contracts

These contracts are defined inline in this specification; no
`docs/contracts/` file is created. Rationale: the house contract template is
HTTP-API-shaped (authentication, endpoints, error semantics) and does not map
to file formats plus CLI behavior; the machine-checkable authority for each
format is the format definition below plus the scenarios; and house precedent
(SPEC-20261016-01, SPEC-20261017-01, SPEC-20261019-01) accepts inline
contracts with stated rationale.

### roundhouse.json vocabulary

A package's `roundhouse.json` is a JSON object with exactly these members:

- `kind` — optional; one of `core`, `workflow`, `capability`, `bundle`;
  absent only for installation tooling (the CLI declares none,
  DEC-20261017-02). Kind is taxonomy metadata: it has no compositional
  effect — contributions drive composition identically for every kind.
- `contractVersion` — required integer; currently `1`. The CLI composes
  packages whose `contractVersion` equals its supported version; any other
  value fails (contracts incompatible).
- `skills` — required array of skill-ID strings, possibly empty. Each ID is
  globally unique per installation and equals its managed directory name: the
  managed-path convention places the skill's entry file at
  `managed/skills/<id>/SKILL.md` in the owning package, composing to
  `.opencode/skills/<id>/SKILL.md` in the consumer. Additional files within
  `managed/skills/<id>/` are owned content. The array is validated
  bidirectionally against the package's `managed/skills/` subtree:
  declared-but-missing (no `SKILL.md` at the convention path) and
  present-but-undeclared (a `SKILL.md` with no declaration) both fail.
  Non-skill managed content needs no per-file declaration — the package's
  `managed/` tree is its owned managed set.
- `bash` — required array of allow-pattern strings, possibly empty. Each
  entry is a single command-matching pattern exactly as it should appear as a
  key in the rendered bash permission map with value `"allow"`; the pattern
  language is OpenCode's own matching semantics, and entries are rendered
  verbatim. Packages declare allow patterns only.
- `requires` — required array of package-name strings, possibly empty, per
  DEC-20261017-02's dependency rules. Every entry must resolve within the
  discovered set; the requires graph must be acyclic (a cycle fails
  composition), and the dependency rules are validation failures, not
  authoring guidance: a capability or workflow package whose `requires`
  omits `@backshop/roundhouse-core`, or a framework or CMS package whose
  `requires` omits its applicable language package, fails composition.

No additional members are permitted. Examples (fixture-shaped):

```json
{
  "kind": "capability",
  "contractVersion": 1,
  "skills": ["lang-javascript"],
  "bash": ["npx jest *"],
  "requires": ["@backshop/roundhouse-core"]
}
```

```json
{
  "contractVersion": 1,
  "skills": [],
  "bash": [],
  "requires": []
}
```

### Core template

The template lives in the core package as content at
`packages/roundhouse-core/opencode-template.json` — a package-root file,
sibling of `roundhouse.json`. It is the one addition to DEC-20261017-02's
package layout, Core-only. It is composer input, never managed content: it is
not copied into the consumer tree; the rendered `opencode.json` is.

Before every render the CLI validates the template against Core's stable
contract:

1. It parses as JSON.
2. The `agent` map carries exactly eight entries: the four Core agents
   (`orchestrator`, `document-author`, `implementor`, `reviewer`) and the
   four built-ins (`build`, `plan`, `general`, `explore`) each
   `{ "disable": true }`.
3. Each Core agent carries `mode`, its tuning member (`steps` for the
   orchestrator; `temperature` for each subagent, matching the shape
   authority), and a `permission` block.
4. Each Core agent's `permission.skill` map is exactly `{ "*": "deny" }` —
   the deny-all wildcard and no allow entries (uniform availability leaves
   nothing for a template allow entry to mean).
5. Each Core agent's `bash` member, when present, is a map — never a bare
   deny string. Rationale: the renderer unions package patterns into a map;
   a bare string is outside the renderer's input domain. Phase 5
   consequence: the reviewer's current bare `"bash": "deny"` posture
   normalizes to a `{ "*": "deny" }` map at template instantiation.
6. `default_agent` is present and names one of the four Core agents.

Every violation fails closed: exit 1, nothing rendered, the invariant and the
offending agent or member named on stderr. The contract exists to catch the
unexpected, not accommodate the routine: Core evolution within the contract
flows without a CLI release; evolution outside the contract forces a
deliberate CLI+Core coordinated update, with the fail-closed error as the
forcing function. Workflow logic lives in skills — the agents are stable
dispatchers, and Core's evolution surface stays minimal.

### Rendered opencode.json

The rendered `opencode.json` looks like today's root file with computed skill
allowlists. The composer renders the template object and touches exactly two
things per Core agent — the skill map and the bash map; everything else,
template member order included, renders verbatim.

- **Skill maps (computed uniform).** Each Core agent's rendered
  `permission.skill` map is the template's deny-all wildcard followed by
  every installed skill — the byte-wise-sorted union of all discovered
  packages' `skills` arrays — each with value `"allow"`. The map is identical
  across the four agents.
- **Bash maps (two layers).** Each Core agent's rendered `permission.bash`
  map is the template's role-driven entries verbatim in template order,
  followed by the union block: the byte-wise-sorted union of all discovered
  packages' `bash` patterns, each with value `"allow"`, excluding patterns
  already present in that agent's template map. A package pattern colliding
  with a template entry carrying a non-`allow` value fails composition; a
  collision with an identical allow value is idempotent (the template entry
  stands, the union block skips it). If the template agent declares no bash
  map, the rendered map contains only the union block.
- **Distinguishability.** The union block is contiguous, last within its map,
  and sorted; verify recomputes it from the discovered packages'
  `roundhouse.json` files and asserts the rendered block equals it. The two
  layers are therefore distinguishable in the rendered output by position and
  verifiable from package declarations.
- **Uniform-bash consequence.** All four agents receive the union — including
  the reviewer (whose template posture today is a bare bash deny) and the
  orchestrator (which today declares no bash map). This follows from the
  ruled model: loading is unrestricted, so every agent that can load a skill
  needs the bash commands that skill declares; role boundaries remain the
  template's tool permissions and the agent prompts.

### .roundhouse/manifest.json

The manifest is a JSON object with exactly these top-level members, in this
order:

- `schemaVersion` — integer, currently `1`.
- `composer` — string, `"<cli package name>@<version>"`: the CLI that
  produced the file.
- `packages` — array of per-package objects, sorted ascending byte-wise by
  `name`. The manifest records every discovered package — the complete
  installed set — including kind-less tooling packages with empty
  contributions.
- `composed` — object mapping composed-artifact paths to their verification
  info; currently exactly one entry, `"opencode.json"`.

Each `packages` entry is an object with members in this order:

- `name` — string; the npm package name.
- `version` — string; the resolved version.
- `contractVersion` — integer; the package's declared contract version.
- `skills` — array of skill-ID strings, sorted ascending byte-wise.
- `managed` — array of `{ "path", "sha256" }` objects sorted ascending
  byte-wise by `path`: every managed file the package owns, at
  consumer-root-relative POSIX paths, with the SHA-256 of the package's
  source file at compose time.
- `seeds` — array of consumer-root-relative POSIX path strings, sorted
  ascending byte-wise: the seed paths the package offers.

The `composed` entry for `"opencode.json"` is an object with members in this
order:

- `sha256` — string; SHA-256 of the rendered file as of the last compose.
- `templateSha256` — string; SHA-256 of the template as of the last compose.

The recorded hashes make the manifest self-sufficient for drift detection
without package sources present; the authoritative verify comparison remains
consumer-file-versus-source byte-equality. Serialization canon: UTF-8 without
BOM; LF line endings; two-space indentation; the member orders above; a
single trailing newline.

### Fixture packages

Fixture packages live at
`packages/roundhouse-cli/test/fixtures/<fixture-name>/` — the CLI package's
test area, checked in, reviewable as test contracts, and reusable by Phase
7's composition matrix. A fixture is a complete minimal package:

- `package.json` — with a `name` in the reserved `@roundhouse-fixture/`
  scope (never published, never resolved from a registry).
- `roundhouse.json` — valid per the vocabulary above.
- `managed/` and `seed/` trees — present when the fixture exercises managed
  or seed behavior; absent otherwise.
- `opencode-template.json` — for core-kind fixtures, a fixture template valid
  per the template contract (or, via copy-and-mutate in temp space, an
  invalid variant exercising one invariant).

Tests compose fixture sets into temporary consumer trees; the format supports
copy-and-mutate so invalid variants need not each be checked in. Fixture
directory names are kebab-case. The specific fixture inventory is plan-level;
every scenario below is constructible under this format.

### Command semantics

Invocation: `roundhouse <command>`. Exit codes mirror the fixture generator:
0 success, 1 failure, 2 usage error. All failures, removals, creations, and
warnings are listed on stderr; nothing silent.

- **`roundhouse init`** — for a fresh consumer: discover from declared
  dependencies and workspace members → validate (vocabulary, contract
  versions, requires resolution, requires-graph acyclicity, the
  DEC-20261017-02 dependency rules, ownership conflicts, template invariants,
  declared-versus-actual skill content, skill frontmatter-identity — each
  SKILL.md's frontmatter `name:` must equal its directory ID) → create
  `.roundhouse/manifest.json`
  → compose managed artifacts and the rendered `opencode.json` → create
  missing seed artifacts. init never deletes: no stale removal, no seed
  overwrite. An existing manifest is an error (exit 1) directing to compose.
- **`roundhouse compose`** — requires an existing manifest (exit 1 directing
  to init otherwise): re-discover → recompute the normalized capability graph
  → validate (the same validation set init performs, including the skill
  frontmatter-identity class) → update managed
  artifacts → remove stale managed files by
  recorded ownership (recorded-but-no-longer-owned; each removal listed on
  stderr; never-recorded files are never removed) → regenerate
  `opencode.json` → create newly applicable seed files only when missing →
  refresh `.roundhouse/manifest.json`.
- **`roundhouse verify`** — read-only; requires an existing manifest (exit 1
  otherwise, directing to init). The composition-input validation (including
  the skill frontmatter-identity class) runs through verify's shared
  pipeline, so verify exits 1 on an identity mismatch. Checks: required
  packages resolve; contracts are compatible;
  ownership is conflict-free; the effective `opencode.json` matches the
  recomputed composition (byte-equality against the canonical re-render);
  managed files match package sources; no tracked managed file is stale or
  unexpectedly missing; expected seed files that have never been created are
  reported. Verify writes nothing; every finding is listed on stderr; exit 1
  on any finding, 0 when clean.

Any unknown command or unexpected argument is a usage error: exit 2, usage
text on stderr, nothing written.

## Branch truth rules

- Per command: init on a fresh consumer → full composition, exit 0
  (SCEN-052); init with an existing manifest → exit 1, directing to compose
  (SCEN-065). compose without a manifest → exit 1, directing to init
  (SCEN-065); compose with one → recompute, update managed, remove stale by
  recorded ownership, regenerate, seed-if-missing, refresh (SCEN-053..055).
  verify without a manifest → exit 1, directing to init (SCEN-065); verify
  with one → read-only report, exit 1 on any finding, 0 clean (SCEN-056).
- Discovery: a declared dependency or workspace member exposing a valid
  `roundhouse.json` → discovered; one with no `roundhouse.json` → not a
  Roundhouse extension, skipped without error; one with an invalid
  `roundhouse.json` → fail closed (SCEN-057..059, SCEN-066).
- Template: valid → rendered; any invariant violated → exit 1, nothing
  rendered (SCEN-060).
- Composition inputs: every violation in SCEN-063's outline → exit 1,
  nothing written; clean inputs → compose proceeds.
- Skill identity: a skill's SKILL.md frontmatter `name:` equals its directory
  ID — a composition-input invariant validated from the discovered set
  (SCEN-074, SCEN-063's outline row), distinct from verify's tree-vs-manifest
  drift classes (working-tree vs committed-artifact); it fails closed
  wherever the shared composition-input validation runs (init, compose, and
  verify's inherited rejection). The convention is pinned: the frontmatter's
  first key must be `name:` and its value unquoted, so the composer's
  parsing and this contract agree.
- No configuration, feature-flag, or environment branches exist; the state
  variables are the command, the discovered set, the template's validity, and
  the consumer tree's drift state.
