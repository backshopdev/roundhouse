# SPEC-20261019-01: Phase 2 workspace scaffolding

## Purpose

Define the Phase 2 scaffolding target state: the conversion of the repository
root into a private npm-workspace shell and the creation of 28 empty package
stubs under `packages/`, so the Phase 2 implementation plan and any scaffold
mechanism have a stable, reviewable definition. The package set is not
hand-chosen: it is derived mechanically from the committed Phase 1 baseline
fixture's ownership annotations (SPEC-20261017-01), so the scaffold reflects
the taxonomy's content-bearing shape as already ruled. No production source
moves; the stubs are minimal envelopes that Phase 3 (composer), Phase 4 (Core
decoupling), and Phase 5 (atomic content cutover) build on (DEC-20261017-03).
This specification describes proposed behavior subject to human and review
signoff; `Active` is its document lifecycle status, not evidence that the
scaffolding has been performed.

## Scope

### Included

- **The root conversion, field-level.** The root `package.json` keeps its name
  `@backshopdev/roundhouse`, gains `private: true` and
  `workspaces: ["packages/*"]`, preserves `scripts` and `engines` verbatim,
  and sheds its publish-oriented fields. The exact field-level effect is
  specified in Public contracts (Root package.json post-conversion); the root
  is the workspace shell, not a package.
- **The 28-package derivation rule.** The scaffolded set is exactly the
  deduplicated `intendedPhase5Owner` values on the committed fixture's managed
  entries that are package names, which today yields `@backshop/roundhouse-core`,
  `@backshop/roundhouse-cli`, and 26 family packages (Public contracts,
  Scaffolded package set). Owner values in `TODO: <rationale>` form —
  human-authored rationale annotations, distinct from the generator's
  pending marker (SPEC-20261017-01) — select nothing; future and reserved
  families have no owner values at all.
  Excluded packages join when their content exists (Phase 5), not at
  scaffolding time.
- **The stub formats.** Each scaffolded package carries exactly two files — a
  minimal `package.json` stub and a minimal `roundhouse.json` envelope — at
  `packages/roundhouse-<subject>/`; the `managed/` and `seed/` directories are
  absent (DEC-20261017-02: directories may be absent when a package has
  nothing of that class). Formats in Public contracts.
- **The fixture regeneration in the same changeset.** The scaffold's new files
  are tracked paths, so the committed fixture regenerates in the same
  changeset that lands the scaffold (SPEC-20261017-01's generator); the
  regeneration adds the new root-scope entries and updates the root
  `package.json` entry's hash.

### Excluded

- **Production source moves.** `src/` is byte-identical before and after; the
  packages are empty shells. Content migration is Phase 5's atomic cutover.
- **The detailed capability schema.** Stubs carry empty `capabilities` and
  `requires` collections only; the capability vocabulary, `availableTo` agent
  lists, and dependency edges are Phase 3 composer territory
  (DEC-20261017-02).
- **Org-package npm naming.** `backshopdev-*` package names are deferred by
  DEC-20261017-02 (Follow-up); no org package is scaffolded.
- **Publishing and Changesets.** Phase 9 territory; every stub is
  `private: true` as a safety until then, and no publish-oriented field
  appears anywhere in the scaffold.
- **The legacy-publish assertions in `scripts/test-package.js`.** The
  root-manifest license assertion and the tarball-allowlist and pack
  behavior depending on the dropped `files`/`version` fields become
  inapplicable under the converted root; their rework or retirement
  disposition belongs to the Phase 2 implementation plan, which must not
  write verification criteria assuming the suite's current green state.
  (Adjacent latent item: `.github/workflows/publish.yml`'s publish
  assumptions lapse under a private root — Phase 9 territory.)
- **The DEC-20261017-03 deprecation amendment.** The softening context — no
  external consumers of the legacy `@backshopdev/roundhouse` package exist, so
  Phase 9's ceremony reduces to `npm deprecate` at most — is recorded by
  amending that decision; it is a related follow-up, out of this
  specification's scope, and imposes no requirement here.
- **The scaffold mechanism.** This specification defines the target state, not
  how the changeset is produced; mechanism choice (hand-authored, generated,
  or scripted) belongs to the Phase 2 implementation plan.

### Dependencies

- DEC-20261017-02: Package contract — primary normative source; the stub
  manifests instantiate its layout, kinds, and manifest model.
- DEC-20261017-03: Migration strategy — defines Phase 2 (workspace
  scaffolding, no production source moved) and the changeset-granularity
  guidance the scaffold follows.
- SPEC-20261017-01: Fixture tooling — the committed fixture whose owner
  distribution derives the package set, and the generator the same-changeset
  regeneration runs.

## Terminology

| Term | Meaning |
| --- | --- |
| Workspace root | The repository root `package.json` after conversion: named `@backshopdev/roundhouse`, `private: true`, declaring `workspaces: ["packages/*"]`. The workspace shell, not a package. |
| Workspace member | A package directory under `packages/` selected by the workspace glob; each of the 28 scaffolded packages is one. |
| Stub | The minimal placeholder manifest pair (`package.json` + `roundhouse.json`) a scaffolded member carries until Phase 5 lands its content. |
| Scaffold | The Phase 2 changeset's result: the converted workspace root plus the 28 member stubs, with no production source moved. |

## Constraints

- **Private root.** The root carries `private: true` and is never publishable;
  it is the workspace shell, not a package.
- **No source moves.** `src/` is untouched; every scaffolded member is an
  empty shell whose only content is its two stub manifests.
- **Node 24.** The root keeps `engines: { "node": ">= 24.0.0" }` and every
  stub declares the same spelling as the root's engines field.
- **Derivation rule.** The scaffolded set is exactly the deduplicated
  package-name owner values from the committed fixture's managed entries — 28
  today. No package is hand-added or hand-omitted; a set that disagrees with
  the fixture's owner distribution is a defect.
- **Minimal envelopes.** Stubs carry no capability content: empty collections,
  no `managed/`, no `seed/`. The detailed capability schema is Phase 3
  territory.
- **Same-changeset fixture regeneration.** The fixture regenerates in the same
  changeset as the scaffold; the new stub files are tracked paths and appear
  in the regenerated fixture.

## Quality attributes

- **Determinism:** Applying the derivation rule to the committed fixture
  yields exactly the 28-package set, and the stub formats pin every field
  value except the human-authored one-line descriptions; re-deriving from the
  same inputs reproduces the same tree.
- **Inspectability:** The `packages/` tree enumerates the taxonomy's
  content-bearing packages at a glance; each stub is small enough to review in
  full; the fixture diff shows exactly which paths the scaffold added and that
  no `src/` hash changed.

## Public contracts

These contracts are defined inline in this specification; no
`docs/contracts/` file is created. Rationale: the house contract template is
HTTP-API-shaped (authentication, endpoints, error semantics) and does not map
to manifest file formats; the machine-checkable authority for each format is
the format definition below plus the scenarios that inspect the real tree; and
house precedent (SPEC-20261016-01, SPEC-20261017-01) accepts inline contracts
with stated rationale.

### Per-package package.json stub

Exactly these members, no others:

- `name` — `"@backshop/roundhouse-<subject>"`, equal to the fixture owner
  value for that member.
- `version` — `"0.0.0"`.
- `private` — `true` (safety until Phase 9 publishing decides otherwise).
- `description` — a non-empty single-line string, one per package
  (human-authored content, not mechanically derived).
- `engines` — `{ "node": ">= 24.0.0" }`, the Node 24 requirement matching the
  root's.

Example (the `lang-javascript` member; the description text is a placeholder,
not normative content):

```json
{
  "name": "@backshop/roundhouse-lang-javascript",
  "version": "0.0.0",
  "private": true,
  "description": "<one-line description>",
  "engines": { "node": ">= 24.0.0" }
}
```

### Per-package roundhouse.json stub

Exactly these members, no others:

- `kind` — present for Core and family packages, absent for the CLI
  (DEC-20261017-02: the CLI is installation tooling and declares no kind).
  Value `"core"` for `@backshop/roundhouse-core`; `"capability"` for each of
  the 26 family packages.
- `contractVersion` — `1`.
- `capabilities` — `[]` (empty; the detailed capability schema is Phase 3
  territory).
- `requires` — `[]` (empty; dependency edges are declared when Phase 5 content
  lands).

The `managed/` and `seed/` directories are absent from every stub
(DEC-20261017-02: directories may be absent when a package has nothing of that
class; they appear when Phase 5 content lands).

Core and family examples:

  "contractVersion": 1,

  "requires": []
}

## Open questions

All three questions were resolved by human ruling on 2026-10-19; the
rulings below are applied in this changeset.

- [x] Root `version` field. The conversion proposes dropping `version` along
  with the other publish-oriented fields — the root is the workspace shell,
  not a package — but npm workspaces roots commonly keep one, and npm's
  tolerance for a versionless root manifest (install, `npm ls`, workspace
  commands) is not verified in this environment. Resolve by experiment or
  ruling: drop, or keep a vestigial version. RESOLVED (human ruling,
  2026-10-19): `version` is dropped. The root is not a package, and private
  roots do not require a version; npm's tolerance for the versionless root
  is verified by an early `npm install` / `npm ls` smoke check that the
  Phase 2 implementation plan owns.
- [x] `engines` spelling. The stub format pins `{ "node": ">=24.0.0" }` while
  the root's existing value is `{ "node": ">= 24.0.0" }` — semantically
  identical ranges, textually different. Rule which spelling is canonical for
  the stubs (and whether the root normalizes to match). RESOLVED (human
  ruling, 2026-10-19): the canonical spelling is the root's existing
  `{ "node": ">= 24.0.0" }` (with the space); the stub format is normalized
  to it in this changeset, and the root's engines field is unchanged.
- [x] `license` disposition. The field-level table classifies `license` as
  package-identity metadata and drops it (the root `LICENSE` file is
  unaffected). If the human prefers keeping `license` in the root manifest as
  repo metadata, only that table row changes. RESOLVED (human ruling,
  2026-10-19): `license` stays dropped from the root manifest; the root
  `LICENSE` file remains the license source.

## Branch truth rules

- The scaffold state is binary. Scaffolded → the tree matches the contracts
  above (SCEN-046..051). Not scaffolded → no `packages/` entries exist and the
  root keeps its pre-conversion single-package manifest.
- No configuration, feature-flag, or environment branches exist: the scaffold
  has no runtime behavior; the only state variable is whether the changeset
  has landed.
- The 28-package set is the derivation rule's instance against the fixture as
  committed; the rule, not the count, is the durable contract (a future
  fixture with different owner values derives a different set by the same
  rule).
