# DEC-20261112-01: The npm publishing model — independent versions, one-command base, manual publish

Status: Active
Last modified: 2026-11-12
Date: 2026-11-12
Context owner: (workflow harness repo)

## Context

The migration (DEC-20261017-01..04) decomposed the legacy single-package
`@backshopdev/roundhouse` into 33 npm-workspace packages: the CLI
(`@backshop/roundhouse-cli`, pure machinery — bin + composer library,
envelope `skills: []`, contributes zero content), Core
(`@backshop/roundhouse-core`, `kind: "core"` — the 4 agent prompts, 15 core
skills, the autonomy workflow docs, `docs-check.js`, the seed scaffolding,
and the composed-render template), and 31 capability packages
(specialist skills). Every package is currently `private: true` at
`0.0.0` — nothing has been published from the new family. Changesets was
adopted in Phase 9 for independent workspace versioning
(`@changesets/cli` 3.0.3 pinned; `updateInternalDependencies: "patch"`
already configured; two changeset files pending in `.changeset/`). The
README's Packaging section is a placeholder deferring to this model.

Distribution by composition — not `npm install` of content — is the
workflow's own mechanism. Packages are source material; the composer
(`init`/`compose`) materializes the workflow into a consumer project, and
the never-recorded policy (SPEC-20261019-02 SCEN-054) makes
consumer-authored `.opencode/` content persist across composes. npm is
the *delivery* channel for that source material, not the runtime.

**Purpose of this record.** This decision had already been made once in
an earlier session, but its reasoning was never written down — the
discussion lived only in chat history. In the 2026-11-11/12 Socratic
interview the maintainer re-derived the model from first principles and,
in the process, nearly undid the existing design (flirted with merging
the CLI into Core) before re-landing on it. This record exists so that
nobody — including future maintainer sessions — ever needs to remember
the reasoning again: chat history is not the record; this file and its
index row are.

## Decision drivers

- **Public availability.** People who want to use Roundhouse must be able
  to get it from npm under the `@backshop` scope. The first consumer is
  the maintainer, installing Roundhouse at work from npm.
- **One-command base.** A consumer installing the base workflow should
  run one `npm install` command and have a complete, composable
  installation — never an empty scaffold.
- **Tool/data separation.** The CLI is machinery and contributes zero
  content; Core is content. The composer must remain invisible to its
  own composition (the root manifest's 62 managed files include none
  from the CLI). This is a clean invariant worth preserving.
- **Independent versioning.** Changesets' per-package versioning and its
  `updateInternalDependencies: "patch"` propagation must keep working
  unchanged.
- **À-la-carte extensibility.** Any of the 31 capability packages can be
  a consumer's chosen add-on; there is no curated-only publish subset.
- **Low-ops release burden.** A solo maintainer should not need a
  secrets-bearing CI release pipeline before a team needs one.

## Alternatives considered

### Alternative A: Two explicit installs (CLI and Core as separate commands)

**Description:** Keep the CLI and Core as decoupled packages with no hard
dependency; the consumer runs `npm install @backshop/roundhouse-cli
@backshop/roundhouse-core` (two declarations) to obtain the base.

**Advantages:**

- Maximum decoupling between tool and content.
- No version-range coupling to maintain.

**Disadvantages:**

- Two commands instead of one.
- The empty-scaffold failure mode returns: a CLI-only install has
  nothing to compose — the agent prompts are Core content — and the
  resulting error/confusion is exactly what a first-time consumer must
  not hit.

### Alternative B: Merge the CLI into Core (single package)

**Description:** Collapse tool and content into one package so a single
install lands everything by construction.

**Advantages:**

- One artifact; no dependency wiring at all.
- The base cannot be split by a wrong install.

**Disadvantages:**

- The tool composes itself: the package would contribute managed files
  *and* be the composer, forcing a "skip myself" special case that
  breaks the clean tool/data invariant.
- Versions couple: a content-only Core change would release the
  composer binary too.
- The merged package would want the name `@backshop/roundhouse`,
  entangled with the legacy package's deprecation story.

### Alternative C: CI-automated publish

**Description:** The standard `changesets/action` GitHub workflow with an
`NPM_TOKEN` secret, publishing on merge to `main`.

**Advantages:**

- Zero manual release steps.
- Publishing cannot be forgotten.

**Disadvantages:**

- A secrets-bearing release workflow before a team needs one.
- Adds ongoing workflow maintenance for a solo-maintainer cadence.
- Trivially additive later; nothing upstream changes when it is adopted.

## Decision

**The npm publishing model is: all 33 packages publish publicly under
the `@backshop` scope with independent Changesets-driven versions; the
CLI declares Core as a hard dependency so the base installs in one
command; the maintainer publishes manually via `changeset publish`; the
legacy package is deprecated, not replaced.** The seven rulings:

1. **Goal.** Public npm availability under the `@backshop` scope for
   people wanting to use Roundhouse; the first consumer is the
   maintainer (installing at work from npm).
2. **Consumption model.** Standard npm flow. The consumer commits
   dependency declarations (`package.json`) and the composition record
   (`.roundhouse/manifest.json` + `opencode.json`) — never
   `node_modules/` or the materialized `.opencode/`. Teammates install
   and compose. Packages are source material; the composer's
   `init`/`compose` materializes the workflow into the project.
3. **Surface.** All 33 packages publish. Any package can be a
   consumer's chosen add-on; there is no curated-only subset.
4. **Structure.** The base workflow is CLI + Core. The 31 capability
   packages are à-la-carte add-ons chosen by devs.
   Consumer-authored custom content is a first-class third path — the
   never-recorded policy's (SPEC-20261019-02 SCEN-054) intended use.
5. **Dependency design.** `@backshop/roundhouse-cli` declares
   `@backshop/roundhouse-core` as a hard dependency, so
   `npm install @backshop/roundhouse-cli` lands the complete base in
   one command. (Reasoning in Rationale.)
6. **Publish flow — manual.** The maintainer runs `changeset publish`
   from their machine when they decide it is time. Batching is the
   accumulate-and-cut model: changeset files queue with no timer; the
   version PR is the cut and takes the maximum bump level per package;
   the changelog carries all pending descriptions together. Manual is
   plausible for the project's life; automating later (the standard
   `changesets/action` with an `NPM_TOKEN` secret) changes nothing
   upstream.
7. **Legacy deprecation.** DEC-20261017-03's softening stands: the
   legacy `@backshopdev/roundhouse` publishes nothing new; at most
   `npm deprecate` on already-published versions (no known external
   consumers). Execution timing is deferred to the implementation plan
   — this record cross-references, it does not re-rule.

## Rationale

The dependency ruling (ruling 5 — the interview's second option, not
this record's Alternative B, the rejected merge) carries the decision's
weight:

- **One command eliminates the empty-scaffold failure mode.** A
  CLI-only install has nothing to compose — the agent prompts are Core
  content — so a hard dependency makes the broken state unrepresentable
  rather than merely discouraged.
- **Tool/data separation is preserved.** The CLI contributes zero
  content and is invisible to its own composition: the root manifest's
  62 managed files include none from the CLI. This clean invariant
  would be broken by a merged package, which would force a "skip
  myself" special case in the composer.
- **Independent versioning is preserved.** Changesets'
  `updateInternalDependencies: "patch"` propagates Core bumps into the
  CLI's range automatically — the hard dependency costs no manual
  coordination.
- **A merged package would want the name `@backshop/roundhouse`,**
  entangling a new artifact with the legacy package's deprecation
  story (ruling 7).

Alternative A was rejected because two commands reintroduce the
empty-scaffold confusion the hard dependency removes, for a decoupling
we have no use for. Alternative B was rejected for the self-composition
special case, version coupling, and the name baggage. Alternative C was
rejected *for now* — not on the merits, but on timing: it is trivially
additive later and changes nothing upstream.

## Consequences

### Positive

- Consumers get the complete base workflow with one
  `npm install @backshop/roundhouse-cli`.
- All 31 capability packages remain individually installable add-ons.
- The CLI's zero-content invariant and the composer's
  invisible-to-itself property survive into the published family.
- The release flow stays a maintainer-side `changeset publish`; no CI
  secrets exist until a team needs them.

### Negative

- Publishing is manual and can be forgotten; forgetting delays
  consumers, nothing breaks.
- The first publish is a mass event: 33 packages at once.
- The `@backshop` org must exist on npmjs with the maintainer as owner
  before anything can publish (real-world prerequisite, verification
  pending — see Assumptions).

### Follow-up

- Wire the hard dependency: `@backshop/roundhouse-cli` declares
  `@backshop/roundhouse-core` as a dependency (ruling 5); its
  `package.json` currently has no dependencies field.
- Flip all 33 packages from `private: true` to publishable.
- Change `.changeset/config.json` `access` from `"restricted"` to
  `"public"`.
- Give the README's Packaging section real content (it currently
  defers to this model).
- Restore `check-pack`'s purpose: publishability-shape verification,
  deferred from CI pending this model, now has a model to verify
  against.
- The two pending changeset files in `.changeset/` become the first
  version PR's content.
- Execute the legacy `npm deprecate` (timing deferred to the
  implementation plan; ruling 7 / DEC-20261017-03).

## Assumptions

- The `@backshop` org exists on npmjs with the maintainer as owner — to
  be verified during planning; publishing is blocked until confirmed.
- Composer discovery semantics (SPEC-20261019-02 SCEN-058): whether a
  hard-dep Core is always-composed or opt-in at the consumer's
  declaration is plan-phase diligence. Either way the base works: if
  discovery is declaration-driven, the hard dependency *is* the
  declaration.

## Reconsider triggers

- A co-maintainer joins — revisit CI-automated publish
  (Alternative C).
- The general-composer use case materializes (consumers composing
  non-Roundhouse envelope packages without Core) — revisit the hard
  dependency.
- The npm org/scope situation changes (org unavailable, scope lost,
  ownership dispute) — revisit the `@backshop` scope commitment.
