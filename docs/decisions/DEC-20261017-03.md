# DEC-20261017-03: Migration strategy and ordering

Status: Active
Last modified: 2026-10-18
Date: 2026-10-17
Context owner: (workflow harness repo)

## Context

`DEC-20261017-01` adopts the composable architecture and
`DEC-20261017-02` defines the package contract. This companion record
fixes how we get from the current single-package state to the target
state without losing Roundhouse's current properties: the four-agent
workflow, local self-hosting, managed-vs-seed semantics, deterministic
review and documentation checks, and the ability to compare the
composed root against authoritative sources.

The riskiest property is "no two-canonical-sources state." The current
`src/` tree contains authoritative copies of every skill, every agent
definition, every seed template, and `opencode.json`. Any naive
package-by-package migration that moves some skills into
`packages/<x>/` while leaving `src/.opencode/skills/<x>/` in place
would produce two authoritative trees with unclear synchronization
semantics.

## Decision drivers

- **Atomic content cutover.** At most one transition point exists
  between "old `src/` is authoritative" and "new `packages/*` are
  authoritative". The transition happens in one changeset.
- **Tooling before content.** The composer must exist and be tested
  against fixture packages before any real content moves. This is
  the safety net against duplicate canonical sources.
- **Decouple Core from extensions first.** Core agents and seeds must
  be refactored to stop hard-coding optional extension skill names
  before the content cutover. Otherwise the cutover lands on a Core
  that is not package-safe.
- **Repo-only tooling excluded from published payloads.** The
  Roundhouse repo's local sync / compose wrappers and their tests must
  not appear in any published package tarball.
- **Legacy package transition is explicit.** Repurposing
  `@backshopdev/roundhouse` as Core is not silent. We will publish a
  final 1.0.0 deprecation release redirecting consumers to the new
  package family, then stop publishing.

## Alternatives considered

### Alternative A: Package-by-package migration with `src/` as fallback

**Description:** Move one capability at a time from `src/` into a new
package; keep `src/` authoritative for un-migrated capabilities;
have the composer read from `src/` for un-migrated capabilities and
from packages for migrated ones.

**Advantages:**

- Each step is small and individually reviewable.
- Partial progress is shippable at any point.

**Disadvantages:**

- Two authoritative trees coexist for the duration of the migration,
  which is the exact risk the plan is designed to avoid.
- Conflict resolution between `src/` and `packages/*` for a partially
  migrated capability is bespoke and undocumented.
- The composer must implement two read paths simultaneously.

### Alternative B: Tooling-first atomic cutover (chosen)

**Description:** Phase 1 freezes and characterizes current behavior. Phase
2 establishes workspace scaffolding without moving content. Phase 3
builds the composer against fixtures. Phase 4 refactors Core so it
does not name optional skills. Phase 5 performs one atomic cutover
moving all `src/` content into the new packages in a single changeset.
Phase 6 replaces the repo-local sync tooling. Phase 7 runs a fixture
matrix of representative compositions. Phase 8 deletes `src/` only
after parity is verified. Phase 9 sets up publishing and CI.

**Advantages:**

- At most one changeset has both "old source authoritative" and "new
  source authoritative" simultaneously (the cutover changeset itself).
- The composer is a proven tool before it touches real content.
- Core is package-safe before the cutover, so the new package
  content is the only thing changing.

**Disadvantages:**

- Phase 3 is significant upfront work; no visible capability change
  until Phase 5.
- Phase 5 is a large changeset; its review is correspondingly heavy.
- A defect in Phase 3 surfaces during Phase 5 review and forces
  rework in earlier phases.

### Alternative C: Fork the project to start fresh

**Description:** Build the new monorepo in a separate git repo or
branch; cut over by replacing the old repo's contents with the new
repo's contents.

**Advantages:**

- No risk of contaminating the working tree.

**Disadvantages:**

- Loses git history of all `src/` files.
- Requires parallel maintenance for the duration of the cutover.
- If implemented as a separate repo, consumers see an npm
  discontinuity that is unrelated to the architectural change. A
  branch-only fork avoids that but loses git history on `src/`
  files anyway.

## Decision

**We execute a tooling-first atomic-content-cutover migration.**

### Phase ordering

1. **Phase 1 — Freeze and characterize.** Capture `src/` inventory
   and managed/seed classification as committed fixtures; extend
   existing test suites with the small remaining safety primitives.
   No decomposition yet.
2. **Phase 2 — Workspace scaffolding.** Convert root `package.json` to
   a private workspace root; create empty package directories under
   `packages/*` with initial `package.json` and `roundhouse.json`. No
   production source moved yet.
3. **Phase 3 — Composer against fixtures.** Build
   `@backshop/roundhouse-cli` (`init` / `compose` / `verify`) and test
   it against fixture packages. Still no real content moved.
4. **Phase 4 — Core decoupling.** Refactor Orchestrator, Document
   Author, Implementor, Reviewer prompts and Core `AGENTS.md` /
   `AGENTIC_WORKFLOW.md` to stop hard-coding optional extension skill
   names. Extract the Socratic-interview behavior into a new Core
   `socratic-interview` skill. Add a Core `task-planning` skill
   covering the lightweight Gate 1 plan. Core must remain useful
   with no extension packages installed.
5. **Phase 5 — Atomic source-tree cutover.** Move `src/.opencode/agents/*`,
   `src/.opencode/workflow-docs/autonomy/*`, every current skill, and
   every seed template into the appropriate package source tree in
   one changeset using `git mv` where possible. Decompose
   `src/opencode.json` into a Core invariant base plus per-package
   skill availability contributions; the composer renders the
   effective `opencode.json`.
6. **Phase 6 — Repo-local tooling cutover.** Move
   `package/deploy-roundhouse.js` and `scripts/sync-roundhouse.js`
   under a repo-only `tooling/` area; replace them with wrappers that
   reuse the same composer library against local workspace package
   sources. Preserve managed-overwrite vs seed-create-if-missing
   semantics.
7. **Phase 7 — Composition matrix tests.** Test representative
   installations, not just the full Roundhouse repository: core only;
   core + documentation + spec workflow; core + JavaScript; core +
   JavaScript + React; core + JavaScript + domain-web + React;
   core + JavaScript + Astro + Apostrophe; and the full current capability
   set. For each, verify that only installed skills exist and are
   allowed in effective `opencode.json`, that framework / CMS
   dependencies are enforced, that absent optional packages leave no
   dead skill names, that Core agents remain loadable, that review
   skill rules remain coherent, and that seed files are not
   overwritten on recomposition. For the full matrix, compare against
   the pre-migration snapshot and document every intentional
   difference.
8. **Phase 8 — Remove legacy `src/`.** Delete `src/` only after
   package sources are authoritative, local compose / sync works,
   full-composition parity is verified, representative partial
   compositions pass, and no scripts, docs, CI jobs, or agent guidance
   still reference `src/`.
9. **Phase 9 — Publishing and CI.** Adopt Changesets for independent
   workspace versioning. After the 1.0.0 deprecation release, stop
   publishing `@backshopdev/roundhouse`; document the package-family
   replacement. Add CI checks for package contract validation,
   workspace dependency validity, composition matrix tests, local
   root drift, package `files` lists, and
   `npm pack --dry-run` per publishable workspace.

### Recommended changeset granularity

The plan calls out seven recommended changesets:

1. Workspace + package-contract scaffolding (Phases 2)
2. CLI composer + safety tests using fixtures (Phase 3)
3. Core decoupling + Socratic skill extraction (Phase 4)
4. Atomic package-content migration + local tooling cutover (Phases 5–6)
5. Composition matrix tests + legacy `src/` removal (Phases 7–8)
6. Publishing / Changesets / CI migration (Phase 9)
7. Documentation and migration guidance for consumers

This DR does not lock that exact mapping; the orchestrator may
combine adjacent phases where the resulting changeset remains
reviewable, with one exception: Phase 4 (Core decoupling plus new
Core skill creation) and Phase 5 (atomic source-tree cutover) must
remain in separate changesets because their review concerns are
distinct.

### Legacy package

We will **publish a final `1.0.0` deprecation release of
`@backshopdev/roundhouse` and then stop publishing**. The migration
plan allows either stop-publish-immediately or publish-then-stop; we
choose publish-then-stop because it leaves no ambiguity for consumers
between the old name and the new Core, and provides one explicit
on-ramp via the deprecation release's README redirect. Consumers
who depend on the old package will see one final release pointing at
the new package family; the replacement packages will be advertised
in this DR's Follow-ups and in the repo README.

### Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Core accidentally depends on optional packages | Phase 4 search runs as `grep -nE 'react\|specification\|literature-note\|planning-structure\|task-planning\|socratic-interview\|@backshop/' src/.opencode/agents/*.md src/AGENTS.md src/AGENTIC_WORKFLOW.md src/.opencode/workflow-docs/autonomy/*.md` (and any later Core files added) and the result is recorded in Phase 4's plan acceptance criteria; any hit blocks Phase 5. |
| Generated OpenCode permissions drift from current policy | Phase 1 snapshots current effective policy; Phase 7 compares rendered output for the full-package matrix. |
| Managed / seed behavior regresses | Phase 1 Slice B adds the missing symlink/junction and path-escape rejection tests to `scripts/test-sync.js`; the full primitive set lives in `package/deploy-roundhouse.js` and is ported into the composer in Phase 3. Old sync code is replaced (not deleted) in Phase 6; `src/` is deleted in Phase 8. |
| Duplicate canonical sources appear during migration | Phase 5 keeps `src/` authoritative until the atomic cutover; Phase 8 deletes it promptly afterward. |
| Repo-local testing depends on published npm versions | Phase 6 local tooling resolves workspace package source directories directly. |
| Package tarballs accidentally include repo-development tooling | Phase 9 CI runs `npm pack --dry-run --json` per publishable workspace and asserts the resulting `files[]` matches each package's declared `files` allowlist plus the contract-defined composed artifacts (`opencode.json`, `.roundhouse/manifest.json`). |
| Phase 1 hand-mapping of `intendedPhase5Owner` produces inconsistent ownership annotations for managed paths not explicitly covered by `DEC-20261017-02`'s taxonomy | Phase 1 records ambiguous cases as `TODO: <rationale>` in `references/migration-baseline.json`; annotations are reviewed during the Phase 1 plan acceptance, and every entry has a documented owner committed before Phase 5 begins. |

### Definition of done

The reorganization is complete when:

- The root is an npm-workspace monorepo.
- Each current capability has one package owner.
- Core operates without optional packages.
- React / Astro / Apostrophe explicitly layer on JavaScript.
- Spec workflow and contracts explicitly layer on documentation.
- Root `opencode.json` is composed from installed / local package
  metadata.
- Root `.opencode/` is composed from local workspace package sources.
- Repo-only development tooling is not present in published package
  payloads.
- Representative partial package compositions pass.
- The old `src/` tree is gone.
- The Roundhouse repository can still test unpublished changes
  against its own working root installation.

## Rationale

Phase ordering is the load-bearing decision. Putting tooling first
(Phases 1–3) means by Phase 5 we have a proven composer and a
characterized baseline; the cutover is then a content move into a
tool that already works, not a content move into a tool under
construction. Putting Core decoupling before the cutover (Phase 4)
means the cutover lands on a Core that is package-safe; if we cut over
first and refactor Core second, we risk a window in which the new
Core still names optional skills. The legacy package decision is
explicit because the plan requires it;
we choose publish-then-stop because it leaves no ambiguity for
consumers between the old name and the new Core, and provides one
explicit on-ramp via the deprecation release's README redirect,
at acceptable ceremony given the consumer transition cost.

## Consequences

### Positive

- Maximum one canonical-source transition point.
- Composer is a proven tool before it touches real content.
- Core is package-safe before the cutover.
- Tests pin current behavior in Phase 1, so regressions are
  detectable from the first phase onward.
- Definition of done is concrete and checkable.

### Negative

- Phase 5 is a large changeset; its review is correspondingly heavy.
- Phases 1–4 produce no externally visible capability change; the
  migration's value lands all at once.
- If a Phase 3 defect surfaces during Phase 5, rework is bounded
  but not free.

### Follow-up

- Each phase produces its own plan and acceptance criteria; the
  orchestrator drafts them after this DR is approved.
- Phase 9 follow-up: write consumer-facing migration documentation
  (README updates, possibly a one-time migration guide for existing
  `@backshopdev/roundhouse` users).
- Publish a final `1.0.0` deprecation release of
  `@backshopdev/roundhouse` whose README and `package.json`
  `description` redirect consumers to the new package family.
  Author a one-time `references/migrating-from-backshopdev-roundhouse.md`
  in this repo pointing at the new packages and the replacement
  command sequence (`npm install -D @backshop/roundhouse-cli
  @backshop/roundhouse-core ...`).

## Assumptions

- We can complete Phase 3 (composer + fixtures) in one changeset
  without touching real content.
- The current `scripts/test-sync.js` and `scripts/test-package.js`
  are sufficient baseline coverage to port the safety primitives
  into the new composer.
- The four Phase 4 agent prompts can be refactored to stop naming
  optional skills without losing meaningful workflow content.

## Reconsider triggers

- A Phase 3 defect cannot be fixed without restructuring the package
  contract; in that case revisit `DEC-20261017-02`.
- A Phase 4 finding shows that Core depends on a specific optional
  skill so deeply that the workflow becomes incoherent without it;
  promote that skill to Core or accept the degradation.
- A consumer surfaces a use case for the legacy package being
  republished as a redirect; revisit the stop-publishing decision.
