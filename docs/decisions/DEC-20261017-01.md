# DEC-20261017-01: Adopt composable package architecture for Roundhouse

Status: Active
Last modified: 2026-10-17
Date: 2026-10-17
Context owner: (workflow harness repo)

## Context

Roundhouse currently ships as a single npm package,
`@backshopdev/roundhouse` (v0.6.0 at the time of this record). The package
embeds a complete distribution template under `src/`: agent definitions,
skills, workflow documents, seed templates, and a configuration file
(`opencode.json`). Local self-hosted development works by syncing `src/`
to the repository root via `scripts/sync-roundhouse.js`, and consumers
install the package and run `npx roundhouse init` /
`npx roundhouse update` to materialize the same template into their own
projects.

This single-package model has reached the limits of what it can express:

- **Capability coupling.** Every consumer receives every skill and every
  agent, regardless of whether their project is a React app, an Astro
  site, a Node service, or none of the above. There is no way to opt
  out of, say, `specification` (a durable-planning skill) for a
  consumer that only wants the baseline collaboration cycle.
- **Extension ceiling.** Third parties cannot contribute Roundhouse
  capabilities because the only legitimate ownership rule is "everything
  in `src/` belongs to the maintainer." A CMS-specific skill, a new
  language, or a domain expertise package has no place in the
  distribution model.
- **Hard-coded agent prompts.** The four agent definitions name
  specific optional skills (`specification`, `react`, `literature-note`,
  `planning-structure`, etc.) as if they always exist. Core therefore
  cannot describe a useful workflow without the full package.
- **Static `opencode.json`.** Every skill and capability is enumerated
  in the package's `opencode.json` allowlist. As capabilities become
  optional, that file can no longer be a static artifact — it must be
  derived from whatever the consumer has actually installed.
- **Repository/publisher conflation.** The same code path serves three
  audiences: (a) Roundhouse maintainers developing the harness, (b) the
  Roundhouse repo itself using it locally, and (c) downstream consumers
  installing from npm. The current `package/deploy-roundhouse.js` plus
  `scripts/sync-roundhouse.js` express all three in a single module.

A direction-locking document was prepared at
`Roundhouse-Composable-Package-Architecture-and-Reorganization-Plan.md`
(working title; will be moved into `scratch/` for the duration of this
record's review and deleted once this record is approved) describing
the proposed target architecture and a 9-phase migration plan. This DR
record formalizes that direction.

## Decision drivers

- **Progressive disclosure / progressive specialization.** Installing a
  capability must make it *available*; it must not *load* into every
  agent session. This is already a Roundhouse property and must be
  preserved.
- **Self-hosted development.** The Roundhouse repository must continue
  to compose an unpublished working installation into its own root for
  testing. The migration cannot break local development.
- **Stable four-agent workflow.** Orchestrator, Document Author,
  Implementor, and Reviewer must remain the only agent definitions.
  Extension packages specialize these roles through skills and metadata,
  not by patching agent prompts.
- **Composability without ambiguity.** Skill IDs, managed target paths,
  and seed paths must be globally unique per Roundhouse installation.
  Duplicate ownership fails composition — no silent overrides.
- **No two-canonical-sources state.** The migration must not produce a
  period during which `src/` and `packages/*` both contain authoritative
  copies of the same skill.
- **Repository-only tooling excluded from published payloads.** The
  Roundhouse repo's local sync/compose wrappers must not appear in any
  npm tarball consumers receive.

## Alternatives considered

### Alternative A: Stay single-package, add conditional skills

**Description:** Keep `@backshopdev/roundhouse` as the only package.
Allow consumers to declare optional skill bundles in their own
`package.json`, and have `roundhouse update` materialize only the
declared ones. Agent prompts would still hard-code references but
update would skip the missing skills.

**Advantages:**

- Smaller change; no monorepo.
- Reuses existing deploy machinery.

**Disadvantages:**

- No place for third-party Roundhouse extensions to live.
- Agent prompts still name non-existent skills in some compositions,
  which is what we are trying to avoid.
- `opencode.json` still hard-codes a superset; "declaration" is not
  enforced.
- Capability boundaries are encoded in user `package.json` rather than
  in versioned package contracts.

### Alternative B: Fork Roundhouse into separate per-capability repos

**Description:** Extract each capability (workflow, language, framework,
CMS, domain) into its own top-level git repository with its own release
cadence. Composer is a small shell script that fetches each repo at
install time.

**Advantages:**

- Maximum isolation; each capability can move independently.
- No monorepo tooling needed.

**Disadvantages:**

- Loses single-PR atomic coordination across capabilities.
- Loses shared tooling, shared tests, shared fixture infrastructure.
- Cross-cutting refactors (renaming a skill across all packages) become
  multi-repo operations.
- The Roundhouse repo's self-hosted development becomes a fragile
  multi-checkout setup.

### Alternative C: Composable npm-workspace monorepo (chosen)

**Description:** Convert the Roundhouse repository into a private
npm-workspace monorepo of independently versioned Roundhouse packages.
A new consumer-facing CLI package
(`@backshop/roundhouse-cli`) implements `init` / `compose` / `verify`.
Each capability package declares a `roundhouse.json` manifest describing
its skills, dependencies, managed files, and seed files. The composer
reads installed packages, builds a normalized capability model, and
materializes the consumer's working installation.

**Advantages:**

- Each capability is a versioned, publishable npm package.
- Third parties can publish Roundhouse extensions under their own
  scopes.
- Composer produces a deterministic composition and a checkable
  `.roundhouse/manifest.json`.
- Roundhouse repo's self-hosted development uses the same composer
  against local packages, not against npm.
- `opencode.json` becomes a composed artifact derived from installed
  skills, not a static template.

**Disadvantages:**

- Larger change than Alternative A.
- Requires a CLI package that does not yet exist.
- Requires refactoring Core agents so they don't name optional skills.
- Requires a migration that moves every existing capability out of
  `src/`.

## Decision

**Roundhouse adopts a composable npm-workspace monorepo architecture.**
The repository becomes a private workspace root. Capability, workflow,
and CLI packages become independent versioned npm packages under the
`@backshop/roundhouse-*` namespace. A consumer-facing CLI
(`@backshop/roundhouse-cli`) implements `init`, `compose`, and
`verify`. The four agent definitions remain in Core and reason from
discoverable installed skills rather than naming optional packages.
The Roundhouse repository's own working installation becomes the
output of the same composer operating on local workspace sources.

Note: the legacy package namespace `@backshopdev/roundhouse` is a
single package; the new family namespace `@backshop/roundhouse-*`
is a family of independently versioned packages.

The supporting decisions are recorded in:

- `DEC-20261017-02` — Package contract and composition rules
- `DEC-20261017-03` — Migration strategy, phasing, and ordering
- `DEC-20261017-04` — Phase 1 commitments (freeze and characterize

## Rationale

The progressive-disclosure / progressive-specialization property is the
load-bearing constraint. Alternative A preserves the single-package
status quo but cannot keep that property as capabilities grow, because
the only way to drop a skill from composition is to edit the user's
project after installation, and there's no enforcement that the
consumer's declared list matches what's actually present. Alternative B
gives up the operational benefits of a monorepo (atomic changes, shared
test fixtures, single-PR coordination) for theoretical isolation we
don't actually need at this scale. Alternative C makes
progressive-disclosure a property of the package contract itself:
install a package, its skills become available to the composer, its
managed files become owned by it, its seed files become creatable on
first install. No skill appears in a composition unless an installed
package contributed it.

The four-agent stability constraint is also load-bearing: replacing or
patching agent prompts is what makes Roundhouse hard to maintain.
Alternative C keeps agent definitions in Core and lets extension
packages contribute only skills and metadata, which preserves the
ability to upgrade Core without coordinating N extension authors.

## Consequences

### Positive

- Consumers install only the capabilities they need; their agent
  sessions load only the skills they have installed.
- Third parties can publish Roundhouse extensions.
- `opencode.json` becomes derived from installed capability metadata,
  so its contents are guaranteed to match the composed installation.
- Roundhouse repository can self-host against local workspace sources
  without publishing.
- Each package versions independently, so a Core change does not
  force a coordinated framework or CMS release.

### Negative

- The migration is large. We will execute it in 9 phases over multiple
  changesets, not one big-bang commit.
- Core agent prompts and `AGENTS.md` / `AGENTIC_WORKFLOW.md` must be
  refactored so they do not name optional extension skills. This is
  content work, not just file moves, and lands in Phase 4.
- The new `@backshop/roundhouse-cli` package must be built and tested
  against fixture packages before it operates on real content
  (Phase 3).
- A non-trivial risk window exists between "new packages exist" and
  "old `src/` is removed"; the plan mitigates this by keeping `src/`
  authoritative until the atomic cutover and deleting it promptly
  afterward.

### Follow-up

- Build `@backshop/roundhouse-cli` (Phase 3) and validate it against
  fixture packages before any `src/` content moves.
- Refactor Core agent definitions and `AGENTS.md` /
  `AGENTIC_WORKFLOW.md` (Phase 4) so they describe a useful workflow
  with no extension packages installed.
- Adopt Changesets for independent workspace versioning (Phase 9).
- Decide the `@backshopdev/roundhouse` legacy package transition in
  Phase 9 (per `DEC-20261017-03`, we will publish a final `1.0.0`
  deprecation release of `@backshopdev/roundhouse` and then stop
  publishing it).
- Move and eventually delete the working analysis document at
  `Roundhouse-Composable-Package-Architecture-and-Reorganization-Plan.md`.

## Assumptions

- The npm-workspace tooling available in Node 24 is sufficient; no
  exotic feature is required.
- Changesets can express independent-versioning-with-bump-propagation
  semantics for the new packages.
- Consumers are willing to depend on multiple `@backshop/roundhouse-*`
  packages instead of one umbrella package; this is consistent with
  modern npm ecosystem practice.
- The existing safety primitives in `package/deploy-roundhouse.js`
  (path containment, symlink/junction rejection, safe recursive copy,
  stale-managed removal, dry-run semantics) are sufficient and can be
  ported into the new CLI package.

## Reconsider triggers

- npm workspaces turn out to be inadequate for some required
  capability (e.g., cross-package circular dependency). If so, revisit
  Alternative B or accept manual coordination overhead.
- A third party needs to extend Roundhouse with capability kinds Core
  does not anticipate. The package contract reserves
  `bundle-` packages but does not define dynamic contribution to
  arbitrary consumer-owned files. If that becomes a real requirement,
  the contract must grow.
- The Core refactor (Phase 4) reveals that one or more optional skills
  is so deeply embedded in agent prompts that the workflow becomes
  incoherent without it. If so, either promote that skill to Core or
  accept that Core's workflow degrades for extension-only consumers.
- Composed `opencode.json` proves materially different from
  hand-authored `opencode.json` in ways consumers depend on (e.g.,
  field ordering, comments, optional sections). The composer must
  reproduce the relevant shape or we must accept the drift.
