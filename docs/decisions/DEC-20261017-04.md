# DEC-20261017-04: Phase 1 commitments — freeze and characterize current behavior

Status: Active
Last modified: 2026-10-17
Date: 2026-10-17
Context owner: (workflow harness repo)

## Context

`DEC-20261017-03` establishes the migration ordering. This companion
record locks the commitments of Phase 1 specifically, because Phase 1
is the first changeset we will execute and it must produce a baseline
that subsequent phases can rely on without re-litigating decisions.

Phase 1 has three slices:

- Slice A — Baseline fixtures (no behavior change).
- Slice B — Test gap fill.
- Slice C — Baseline documentation.

Two of the decisions made during Phase 1 planning are durable enough
to record here rather than defer to the Phase 1 implementation plan:
Core skill extraction (new `socratic-interview` and `task-planning`
skills) and the treatment of existing root seed files as
already-seeded.

## Decision drivers

- **Reproducibility.** Subsequent phases must be able to detect
  drift against a known `src/` state, not against an opaque "current
  state."
- **Coverage of invariants.** The composer in Phase 3 needs to inherit
  the existing safety primitives. Phase 1 ensures those primitives
  are characterizable before they are ported.
- **Core skill coherence.** The `socratic-interview` extraction and
  the `task-planning` introduction must be designed before Phase 4
  executes, not designed inside it.
- **Seed-file semantics for the existing repo.** The current repo
  root already contains files that would be Core seeds under the new
  contract. Phase 1 must fix their semantics so the cutover in
  Phase 5 does not silently overwrite them.

## Alternatives considered

### Alternative A: Minimal Phase 1 — snapshot only

**Description:** Generate a baseline fixture file with hashes and
paths only; do not add tests or documentation.

**Advantages:**

- Smallest changeset.

**Disadvantages:**

- Defers test gap fill to Phase 3, where it competes with composer
  development for review attention.
- Does not lock the Core skill extraction or the seed-from-start
  semantics; those decisions live in chat and risk being lost.

### Alternative B: Full Phase 1 — fixtures + tests + docs + skill design (chosen)

**Description:** Generate baseline fixtures; fill the small
remaining test gaps (symlink / junction and path-escape rejection
in the sync script, root consumer-owned seed preservation tests);
produce a baseline summary document; commit the Phase 1 decisions
about Core skill extraction and seed-from-start semantics.

**Advantages:**

- Aligns with the plan's Phase 1 acceptance criteria
  ("Existing deployment behavior is reproducibly characterized by
  tests").
- Decisions that affect multiple phases (Core skills, seed
  semantics) are durable records rather than chat history.
- Subsequent phases have a baseline they can refer to in their own
  acceptance criteria.

**Disadvantages:**

- Larger Phase 1 changeset than the minimum.
- The Phase 1 decisions about Core skill extraction must be
  consistent with what Phase 4 actually executes; if Phase 4
  discovers an issue, this record must be amended.

## Decision

### Slice A — Baseline fixtures

- Move the working analysis document from repo root to
  `scratch/architecture-rfc.md` so its content remains discoverable
  but is not tracked-as-policy. The moved file is preserved in
  `scratch/` through approval; it will be deleted in a follow-up
  commit after `DEC-20261017-01` through `DEC-20261017-04` are
  approved (i.e., after Phase 1 begins exercising this policy).
- Generate `references/migration-baseline.json` capturing two
  scopes in a single fixture:
  - **Source scope** — every relative path under `src/` (sorted,
    POSIX-style), SHA-256 of each file, the `src/opencode.json`
    SHA-256 and byte size, and a per-entry `classification` field
    (`managed` or `seed`). Each entry is tagged `base: "src"`.
  - **Root scope** — the Roundhouse repository's own working-tree
    surface: every path at repo root that the composer or sync
    tool is expected to leave alone (currently `package.json`,
    `LICENSE`, `guiding-principles.md`, the `references/` and
    `.github/` directory trees, and similar). Each entry is tagged
    `base: "root"` with `classification: "root-only-artifact"`.
  - The union vocabulary (`managed` | `seed` | `root-only-artifact`)
    is kept across both scopes; the `base` field disambiguates
    which classification is meaningful where. Managed and seed
    apply only to `base: "src"`; root-only-artifact applies only to
    `base: "root"`.
- For every managed entry, also record an `intendedPhase5Owner`
  annotation naming the `@backshop/roundhouse-*` package that will
  own the path after the atomic cutover (e.g.,
  `src/.opencode/skills/react/...` →
  `@backshop/roundhouse-framework-react`). The annotation is
  hand-mapped during Phase 1, populated from the package inventory
  in `DEC-20261017-02`, and treated as informational until Phase 5
  enforces it. Seed entries and root-only-artifact entries do not
  carry an owner annotation in Phase 1.
- Add `references/migration-baseline.schema.json` documenting the
  fixture shape (per-entry `path`, `base`, `classification`,
  `sha256`, `sizeBytes`; managed entries additionally carry
  `intendedPhase5Owner`).
- Add a deterministic generator script
  (`scripts/generate-migration-baseline.js`) that the fixture can be
  regenerated from. The fixture file is committed; the generator is
  the source of truth. The generator must not synthesize or guess
  `intendedPhase5Owner` values; the annotation is human-authored
  and committed alongside the generator.
- Tests assert the generator produces an identical baseline on
  rerun and that the baseline matches current `src/` and current
  repo-root content.

### Slice B — Test gap fill

Extend `scripts/test-sync.js` with:

- Symlink / junction rejection mirroring the existing
  `scripts/test-package.js` coverage so the repo-local sync layer
  inherits the same safety guarantees as the consumer CLI.
- Path-escape rejection mirroring the same.
- Tests that existing root consumer-owned seed files
  (`AGENTS.md`, `AGENTIC_WORKFLOW.md`, `BUILDING.md`, `TESTING.md`,
  `CONTRIBUTING.md`, `scratch/README.md`, `ktlo/index.md`,
  `ktlo/template.md`, `docs/index.md`) are preserved untouched by
  sync — they behave identically to seeds from the start.

The existing `scripts/test-package.js` safety primitives (junction
rejection at managed root, nested destination, source-side junctions,
unrelated consumer links, managed type-conflict repair, dry-run
non-mutation, seed preservation) remain in their current location and
are referenced from the baseline summary document.

- A self-hosting verification test: run the (current) sync tooling
  against the Roundhouse repo's own root and assert it exits 0
  with no drift. After Phase 6 this test becomes the assertion
  that the composer, run against local workspace package sources,
  reproduces the repo root. This is the test that makes
  `DEC-20261017-03`'s definition-of-done bullet ("The Roundhouse
  repository can still test unpublished changes against its own
  working root installation") verifiable.

### Slice C — Baseline documentation

Produce `references/migration-phase1-baseline.md` summarizing:

- The captured `src/` inventory and managed / seed / root-only
  classification.
- Which safety tests already existed and which Phase 1 added.
- Which Phase 1 acceptance criteria are now provably satisfied.
- Which Phase 1 risks (per `DEC-20261017-03`'s "Risks and
  mitigations" table) remain unmitigated until later phases.
- Every repo-root path in the seed-from-start list is byte-equal
  to its `src/` source at Phase 1 close. Any non-equality is
  recorded as an intentional divergence in the baseline summary
  and resolved before Phase 5 begins, so the atomic cutover does
  not silently propagate drift.

### Phase 1 durable decisions

**Core skill extraction.** The Orchestrator currently embeds the
Socratic interview behavior inline. We commit to extracting that
behavior into a new Core skill named `socratic-interview` during
Phase 4. The Orchestrator will route to it rather than embedding the
full interview procedure in its prompt.

We additionally commit to adding a new Core skill named
`task-planning` that governs the lightweight Gate 1 plan required
for any Roundhouse task. `task-planning` is distinct from
`planning-structure` (which remains in the `workflow-spec` package
and governs the durable docs-as-code planning model). Core provides
the baseline; the optional workflow-spec package provides the richer
durable workflow.

**Seed-from-start semantics for the existing repo.** Every file
currently living at repo root that would be a Core seed under the
new contract is recorded as already-seeded. The composer (Phase 3)
must never overwrite it on recomposition. The list of these paths
is captured in `references/migration-baseline.json` with
`classification: seed`. Phase 5's atomic cutover must not change
their content; if any of these files legitimately need to be
updated as part of the cutover, the update must be in the cutover
changeset itself, not a Phase 1 / Phase 7 / Phase 9 side effect.

**Root-only-artifact semantics.** `package.json`, `LICENSE`,
`guiding-principles.md`, `references/`, `.github/`, and similar
non-seed paths are classified as `root-only-artifact`. They are
preserved by sync and never overwritten by composer.

## Rationale

The Phase 1 acceptance criteria in the parent plan are explicit
("existing deployment behavior is reproducibly characterized by
tests"). Slice B is what makes the existing safety primitives
characterizable for the composer in Phase 3. The Phase 1 durable
decisions exist because Core skill extraction and seed semantics
affect multiple phases; recording them now means Phase 4 has
direction before it starts and Phase 5 has explicit guardrails.

## Consequences

### Positive

- Phase 3 has a proven baseline to build the composer against.
- Core skill extraction has direction before Phase 4 begins.
- Phase 5's atomic cutover has explicit "do not silently overwrite"
  guardrails for the existing repo's seed files.
- The baseline summary document gives reviewers of subsequent phases
  a stable reference.

### Negative

- The Phase 1 changeset is larger than the minimum; it touches
  fixture files, tests, and documentation.
- The Core skill extraction decision must be revisited if Phase 4
  discovers that `socratic-interview` and `task-planning` cannot
  cleanly replace the in-prompt Socratic behavior.
- The seed-from-start decision locks Phase 5 into "preserve these
  files verbatim"; if any of them legitimately need a content update
  as part of the cutover, that update must be deliberate.

### Follow-up

- Phase 1 follow-up lands in `scratch/architecture-rfc.md`
  relocation and removal after this record is approved.
- Phase 2 follows with workspace scaffolding.
- Phase 4 uses the Core skill extraction decision to scope its
  refactor.
- Phase 5 uses the seed-from-start list as a no-overwrite
  guardrail.
- The deprecation release and migration guide from
  `DEC-20261017-03`'s Follow-up are produced before Phase 9 begins,
  so the consumer-facing transition is visible before npm publishes
  the new packages.

## Assumptions

- The current `scripts/test-sync.js` and `scripts/test-package.js`
  can be extended (not rewritten) to add the new test coverage.
- The Core skill extraction is feasible without losing Socratic
  interview fidelity — the behavior moves into a skill, not into a
  different prompt.
- `references/migration-baseline.json` is small enough to commit
  comfortably (file inventory + hashes + classification, no full
  byte content).
- `task-planning` is authored without importing vocabulary from
  `planning-structure`; any vocabulary overlap is documented in
  Phase 4's plan and not at the policy level. The Core baseline
  remains usable when `workflow-spec` is absent.

## Reconsider triggers

- Phase 1 testing surfaces a safety primitive that does not exist in
  the current code (i.e., the existing tests are insufficient even
  with the additions). In that case the missing primitive must be
  added to `package/deploy-roundhouse.js` and `scripts/sync-roundhouse.js`
  before Phase 3 can rely on it.
- Phase 4 discovery contradicts the Core skill extraction decision.
  In that case `DEC-20261017-04` is amended and Phase 4's plan
  adjusts.
- A seed file in the existing repo root needs content that
  contradicts its seed-template origin. Resolve by either updating
  the seed template (preferred) or marking the root copy as
  root-only-artifact (override).
