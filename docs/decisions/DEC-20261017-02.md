# DEC-20261017-02: Package contract and composition rules

Status: Active
Last modified: 2026-10-19
Date: 2026-10-17
Context owner: (workflow harness repo)

## Context

`DEC-20261017-01` establishes that Roundhouse will be a composable
npm-workspace monorepo. This companion record locks the specific
contract: package naming, layout, kinds, agent ownership rules,
artifact classes (managed vs seed vs composed), ownership conflict
rules, and the consumer CLI surface. These are the rules the composer
must implement; they must be agreed before any package source moves.

**Amendment (2026-10-18).** The naming taxonomy was redesigned in the
2026-10-17/18 taxonomy interview: a nature-based composable taxonomy
replaces the original topic-based families, three explored designs are
recorded under Alternatives considered, and the drivers, rationale,
consequences, assumptions, and reconsider triggers are updated
accordingly. The contract's remaining sections are unchanged except
where the new taxonomy forces wording updates.

**Amendment (2026-10-19).** The uniform-availability ruling carried by
`SPEC-20261019-02` supersedes the `availableTo` member named in Alternative
B's sketch: packages declare skill IDs, and every installed skill is loadable
by every agent; role boundaries are tool permissions and agent prompts, not
skill availability. The contract's remaining sections are unchanged.

## Decision drivers

- **Discoverability.** Consumers should be able to install a package
  and have its capabilities recognized without registering them
  somewhere first.
- **No coupling to OpenCode config shape.** Packages must not embed
  raw `opencode.json` fragments; the composer must translate a
  normalized capability model into whatever shape the current OpenCode
  permissions format requires. This insulates packages from OpenCode
  config churn.
- **Strict ownership.** A skill ID, a managed target path, and an
  agent path must each have exactly one owner. Duplicate ownership is
  a contract error, not a silent merge.
- **Agent stability.** The four agent definitions are Core-owned and
  must not be replaced, patched, or extended by any other package.
- **Reusability across repository and consumer.** The composer used by
  `@backshop/roundhouse-cli` must also serve the Roundhouse repository's
  local self-hosting workflow with the same semantics.
- **The skill is the atom.** Capabilities are narrow, progressively
  discoverable, load-on-demand skills — the descendant of the early
  harness's AGENTS.md lines ("if a mistake is made, add a line").
  Packages curate skills; they do not aggregate topics.
- **Org flavor is swappable.** Generic crafts are true everywhere;
  organization workflow flavor is namespaced and optional, so a
  consumer adopts the crafts without adopting BackShopDev's process,
  or swaps in its own.

## Alternatives considered

### Alternative A: Packages emit raw OpenCode fragments

**Description:** Each capability package ships a literal
`opencode.json` fragment that the composer concatenates into the
consumer's final `opencode.json`.

**Advantages:**

- Reuses OpenCode's existing merge semantics.
- Less translation logic in the composer.

**Disadvantages:**

- Every package is coupled to the current OpenCode config schema.
- Conflict resolution becomes merge-conflict territory, which is
  exactly what we want to avoid at the package-contract layer.
- Capability contracts end up re-encoding skill-allowlist semantics
  inline.

### Alternative B: Normalized capability model with composer translation (chosen)

**Description:** Each package declares its capabilities in a
`roundhouse.json` manifest using a normalized vocabulary (skill IDs,
`availableTo` agent lists, `requires` package dependencies). The
composer builds a graph, validates uniqueness, and renders
`opencode.json` from the normalized model.

**Advantages:**

- Capability contracts are stable across OpenCode config changes.
- Conflict detection is a property of the composer, not of merge
  semantics.
- New capability kinds can be added without touching existing packages.

**Disadvantages:**

- Composer must own the translation; more code than concatenation.
- Some loss of fidelity compared to free-form OpenCode fragments —
  for example, free-form per-package `permission` arrays cannot be
  expressed; the composer only emits canonical `allow`/`deny`
  shapes — but only for things we explicitly chose not to support.

### Alternative C: A `concern-*` family for user-facing quality concerns

**Description:** Add a `concern-*` family for user-facing quality
concerns (`concern-security`, `concern-privacy`,
`concern-accessibility`), parallel to the practice families.

**Advantages:**

- Gives user-facing qualities a visible, dedicated home distinct from
  engineering practice.

**Disadvantages:**

- The concern/topic boundary proved blurry in practice;
  `quality-attributes` stayed software-design subject matter.
- The nature-based principle already assigns these skills a natural
  home: they are software engineering practices, so `software-*`.

**Outcome:** Explored and superseded during the taxonomy interview.
`software-*` is the natural home (`software-security`,
`software-privacy`, `software-accessibility`).

### Alternative D: Org-prefix naming for skill IDs

**Description:** Namespace organization flavor with an org family
prefix on skill IDs (`backshopdev-docs-spec`).

**Advantages:**

- Org skills are visually distinct at a glance.

**Disadvantages:**

- Breaks the base-to-specialization left-to-right readability that
  `lang-javascript-jest` established: the org marker would sit between
  the family and the subject.
- The org suffix composes with the layering grammar as the final
  specialization layer (`docs-spec-backshopdev` builds on
  `docs-spec`); a prefix form cannot express that layering.

**Outcome:** Rejected. Org is a skill-ID suffix when specializing a
generic base, and a family prefix only when the org is the origin of
an original practice with no generic base (`backshopdev-planning`).

### Alternative E: Keeping monolithic `domain-*` craft packages

**Description:** Keep the four domain packages (documentation,
contracts, software-design, web) as craft buckets and map every skill
into one of them.

**Advantages:**

- No migration churn for the four existing packages.

**Disadvantages:**

- Mapping every skill individually showed the domain packages were
  topic buckets mixing natures — a format skill, a language skill,
  and practices in one package.
- Topic domains do not get families under the nature-based principle.

**Outcome:** Rejected. The four domain packages dissolve and their
skills distribute by nature; `domain-*` is redefined for business
domains (problem spaces), reserved with none in v1.

## Decision

### Package layout

Every capability, workflow, and CLI package contains:

```text
package.json
roundhouse.json
managed/
seed/
```

Directories may be absent when a package has nothing of that class.
Repositories and consumers do not see these directories directly; the
composer materializes them into `.opencode/` (managed) or into
consumer-rooted paths (seed) on first install.

### Naming taxonomy

The taxonomy classifies skills by nature; packages curate skills and
declare ownership in `roundhouse.json` (principles 3 and 4). Non-org
packages continue under the repo's `@backshop/roundhouse-*` npm scope;
org packages carry the org as a name prefix (org-naming rule below),
with exact npm naming deferred (Follow-up).
`@backshop/roundhouse-cli` is installation tooling: it declares no
skills and no kind, so it sits outside these families.

#### Design principles

1. **Skills classify by nature, not topic.** A software engineering
   practice is `software-*`; a documentation practice is `docs-*`; a
   data format is `format-*`; an interaction convention is
   `protocol-*`. Topic domains do not get families — their skills
   distribute by nature.
2. **Prefix chains compose.** Skill IDs read
   `<family>-<subject>[-<specialization>…]`, left-to-right as base →
   specialization. A longer name layers on its prefix-truncated
   parent, and the name encodes the dependency edge:
   `lang-javascript-jest` requires `lang-javascript`;
   `docs-software-contracts` is the documentation practice for the
   `software-contracts` subject; `software-accessibility-web` is the
   web-bound specialization of `software-accessibility`.
3. **The skill is the atom.** Narrow, progressively discoverable,
   load-on-demand — the descendant of the early harness's AGENTS.md
   lines ("if a mistake is made, add a line"). Any discrete "thing"
   becomes a skill; packages curate them.
4. **Packages curate; names classify.** Ownership is declared in
   `roundhouse.json` (strict uniqueness), never inferred from name
   prefixes. A package may hold one skill or many; the skill's prefix
   does not mechanically determine its package (`format-markdown` may
   live inside a `@backshop/roundhouse-docs-spec-workflow` package).
5. **Cross-cutting vs. bound.** `software-*` subjects are
   language-agnostic and combine with any `lang-*`/`framework-*`
   stack: `software-security` + `lang-javascript` +
   `lang-javascript-jest` is a coherent installation, and the same
   `software-security` serves a C# shop.
6. **Org flavor vs. generic craft.** Generic crafts (`docs-spec`,
   `software-testing`, `format-markdown`) are true everywhere;
   organization workflow flavor is namespaced and swappable per
   consumer. The org layer is an optional overlay: crafts stand alone
   (a repo may use `docs-implementation-plan` with just a line in its
   AGENTS.md), and an org workflow package defines which crafts a repo
   uses and how they flow.
7. **Fission is normal.** One skill may become a base + specialization
   pair as understanding matures.

#### Families

- **(Unprefixed) Core.** Machinery every installation needs: the four
  agent definitions, the autonomy workflow docs, `docs-check.js`, the
  harness machinery skills (`peer`, `review-findings`, `security`,
  `harness`, `investigation`, `opencode-configuration`, `docs-check`,
  `git-commit`, `commit-convention`, `architectural-coherence`,
  `behavioral-completeness`, `contract-completeness`,
  `decision-quality`), and the `socratic-interview` skill added in
  Phase 4 (DEC-20261017-04). Core skills carry no family prefix.
- **`lang-*` — languages and language-bound specializations.**
  `lang-javascript` (the `javascript` and `typescript` skills fold
  into it), `lang-css` ← `lang-css-sass` (split), `lang-gherkin`
  (split from `gherkin-testability`). Future:
  `lang-csharp`, `lang-python`, `lang-go`, `lang-rust`. Future
  headroom: `lang-javascript-jest`, `lang-csharp-nunit`.
- **`framework-*`.** `framework-react`, `framework-astro`.
- **`cms-*`.** `cms-apostrophe` (from `apostrophe-cms`); future:
  `cms-strapi`, `cms-sitecore`, `cms-sanity`.
- **`tool-*` — build tools.** Future: `tool-vite` (`tool-gulp` and
  `tool-webpack` are family-pattern examples, not planned).
- **`software-*` — cross-cutting software practices.**
  `software-security` + `software-privacy` (the `security-privacy`
  skill splits), `software-quality` (from `quality-attributes`),
  `software-testing` (new), `software-testability` (from
  `design-for-testability`) ← `software-testability-legacy-enablement`
  (from `test-enablement`; Feathers-style seams are a legacy technique
  — greenfield code is designed testable in the base),
  `software-architecture`, `software-design`, `software-contracts`
  (from `contract-design`), `software-compatibility` (from
  `api-compatibility`), `software-accessibility` ←
  `software-accessibility-web` (the `accessibility` skill splits),
  `software-performance` ← `software-performance-web` (the
  `web-performance` skill splits), `software-discoverability-seo` +
  `software-discoverability-ldjson` (from `seo-structured-data`).
  Future headroom: `software-unit-testing`, `software-security-redteam`.
- **`docs-*` — documentation practices.** `docs-spec` (from
  `specification`), `docs-decision-record` (from `decision-record`),
  `docs-implementation-plan` (from `implementation-plan`),
  `docs-architecture` (from `architecture-document`),
  `docs-implementation-map` (from `implementation-map`),
  `docs-literature-note` (from `literature-note`), `docs-publish`,
  `docs-general` (new — the general documentation-quality practice; it
  carries the dictum that documentation gaps are a blocking finding
  and that docs are first-class repo inhabitants updated along with
  code, plus the repo-artifact-system conventions folded in from
  `repository-documentation`: metadata, stable IDs, index discipline,
  archive rules, and lifecycle status) ← `docs-general-accuracy`
  (from `repository-accuracy`),
  `docs-general-traceability` (from `requirements-traceability`),
  future `docs-general-readability`; `docs-software-contracts` (the
  `contract-guide` and `contract-publication` skills fold — generated
  docs serve a mixed agent+human audience). Org customizations suffix
  the generic base: `docs-spec-backshopdev` builds on `docs-spec`.
- **`format-*` — data formats (the shape of data).** `format-markdown`
  (new), `format-json` (new), `format-html` (new) ←
  `format-html-semantic` (from `semantic-html`), `format-json-schema`
  (from `json-schema`).
- **`protocol-*` — interaction conventions.** The rules of how systems
  talk, at the API/architecture level — not wire-level standards:
  `protocol-openapi` (from `openapi`). Future: `protocol-rest`.
  Protocols use formats (`protocol-rest` pairs with `format-json`).
- **`backshopdev-*` — BackShopDev's own practices.** Used across all
  BackShopDev repos (Roundhouse and not-Roundhouse):
  `backshopdev-planning` (from `planning-structure` — the org's
  planning methodology), `backshopdev-testing` (new). The org
  doc-workflow skill — for example, `docs-workflow-backshopdev` —
  lives in a backshopdev package (exact npm naming deferred — see
  Follow-up).
  Org extension rule: a new doc type is just `docs-<newtype>` (for
  example, FooBar, Inc.'s `docs-bambaz`) — no conflict, because skill
  IDs are unique per installation and ownership is per-package.
- **`domain-*` — business domains (redefined).** Problem spaces, not
  crafts: `domain-payments`, `domain-usermanagement`,
  `domain-metrics` style. Reserved; none in v1. The four current
  domain packages dissolve (below).

**Docs-as-code.** Documentation is managed as code — versioned,
reviewed, and validated alongside the software it documents. This is a
core Roundhouse principle, carried by the `docs-*` family and by
`docs-general` specifically.

#### Dissolutions

The four current `domain-*` packages dissolve, and the original
Workflows package dissolves with the taxonomy replacement; their
skills distribute by nature:

- `domain-software-design` → its six skills distribute into
  `software-*` (per the families above).
- `domain-documentation` → `docs-literature-note` (and the `docs-*`
  family generally).
- `domain-contracts` → its six skills distribute by nature:
  `contract-design` → `software-contracts`; `contract-guide` +
  `contract-publication` fold → `docs-software-contracts`;
  `api-compatibility` → `software-compatibility`; `json-schema` →
  `format-json-schema`; `openapi` → `protocol-openapi`. No
  `contracts-*` family exists.
- `domain-web` → its six skills dissolve: `semantic-html` →
  `format-html-semantic`; `css-sass` → `lang-css` +
  `lang-css-sass`; `accessibility` → `software-accessibility` +
  `software-accessibility-web`; `web-performance` →
  `software-performance` + `software-performance-web`;
  `seo-structured-data` → `software-discoverability-seo` (+ future
  `software-discoverability-ldjson`); `image-media-delivery` →
  dropped: a topic bucket, not a nature — its content distributes
  into future `format-*` image skills and
  `software-performance-web`. Recorded as retired.
- `@backshop/roundhouse-workflow-spec` — its skills distribute by
  nature per the families above, including `repository-documentation`,
  which folds into `docs-general`.

#### Org-naming rule

The org marker splits by artifact type:

- **Skill IDs.** Org is always a suffix when specializing a generic
  base: `docs-spec-foobar` builds on `docs-spec`;
  `docs-workflow-backshopdev` defines BackShopDev's doc workflow. The
  org appears as a family prefix only when the org is the origin of an
  original practice with no generic base (`backshopdev-planning`).
- **Package names.** Org is always a prefix: `foobar-doc-workflow`,
  `backshopdev-roundhouse-doc-workflow`. Exact npm scope and package
  naming are deferred to a future naming discussion (Follow-up) and
  are not pinned here.

### Package kinds

`roundhouse.json` recognizes four kinds:

- `core`
- `workflow`
- `capability`
- `bundle`

Languages, frameworks, CMSs, tools, and the `software-*`, `docs-*`,
`format-*`, `protocol-*`, and `backshopdev-*` practice families are
all `capability` packages, as are the reserved business-domain
packages (`domain-*`; none in v1). The org doc-workflow package —
for example, a package carrying the `docs-workflow-backshopdev`
skill — is a `workflow`-kind package. The CLI is installation
tooling and does not declare a kind.

### Agent ownership

Core owns exactly four agent definitions:

- Orchestrator
- Document Author
- Implementor
- Reviewer

Only Core may contribute agent definitions. Extension packages
specialize these stable roles through skills and metadata; they do not
replace or patch agent prompts. Core agent definitions must reason
from assigned / discoverable installed skills and must not hard-code
optional package names.

### Dependency rules

1. Every capability / workflow package requires `@backshop/roundhouse-core`.
2. A specialization requires any lower-level capability whose guidance
   it assumes.
3. Framework packages require their applicable language package.
4. CMS packages require their applicable language package.
5. Domain packages are independent of other domain and practice
   packages unless their guidance actually assumes another package.
6. Dependencies express guidance assumptions, not merely technology
   associations. React does not require `software-accessibility-web`
   because React may be used outside the browser.

### Artifact classes

| Class | Definition | Owned by | Composer behavior |
| --- | --- | --- | --- |
| Managed | Files copied from exactly one package | Single owning package | Copied on compose; removed when owning package is gone |
| Seed | Files created only when absent | First-creating package | Created on `init` if missing; never overwritten on `compose` |
| Composed | Files generated from installed capability model | Roundhouse CLI | Regenerated on every compose; not copied from any package |

Initial composed artifacts:

```text
opencode.json
.roundhouse/manifest.json
```

Adding new composed artifacts requires an explicit architectural
decision; a package may not silently introduce generated-file
semantics.

### Ownership and conflict rules

- **Skill IDs** are globally unique per installation. Duplicate skill
  IDs fail composition.
- **Managed target paths** have exactly one owning package. Duplicate
  paths fail composition.
- **Agent paths** are reserved to Core. Any other package declaring
  one fails composition.
- **Seed path collisions** fail composition. Shared seed scaffolding
  belongs in a lower-level dependency package.
- **Override needs** in v1 must be resolved by changing the package
  that owns the conflicting artifact; the contract does not provide
  a release-merge or accommodation path.

Intentional replacement / override semantics are not part of v1; v1
fails closed on duplicate ownership.

### Consumer CLI

`@backshop/roundhouse-cli` exposes three commands:

- `roundhouse init` — discovers declared Roundhouse packages, validates
  contracts and dependencies, creates `.roundhouse/manifest.json`,
  composes managed and composed artifacts, and creates missing seed
  artifacts.
- `roundhouse compose` — recomputes the normalized capability graph,
  validates conflicts and requirements, updates managed artifacts,
  removes stale managed files by recorded ownership, regenerates
  `opencode.json`, creates newly applicable seed files only when
  missing, and refreshes `.roundhouse/manifest.json`.
- `roundhouse verify` — read-only validation that required packages
  resolve, contracts are compatible, managed ownership has no
  conflicts, effective `opencode.json` matches composition, managed
  files match package sources, no tracked managed file is stale or
  unexpectedly missing, and expected seed files that have never been
  created are reported.

Package install / remove remains npm's job in v1. The CLI does not
wrap `npm install` or `npm uninstall`.

### Package discovery

The composer does not blindly scan `node_modules`. It starts from the
consuming repository's declared `dependencies` and `devDependencies`,
resolves those package roots, and treats a package as a Roundhouse
extension only when it exposes a valid `roundhouse.json`. This permits
third-party Roundhouse extensions outside the `@backshop` scope.

### Manifest

`.roundhouse/manifest.json` is a generated composition / ownership
manifest, not a second hand-maintained dependency list. It records
per package: name, resolved version, contract version, contributed
skills, owned managed paths, offered seed paths, and generated
artifact version / hash information sufficient for verification. The
manifest is committed so composition changes are reviewable.

## Rationale

A normalized capability model keeps packages stable across OpenCode
config changes and lets the composer own conflict detection — both of
which are the load-bearing constraints identified above. Strict
ownership rules are non-negotiable because silent merges are how
harnesses become unmaintainable. Reserving agent paths to Core
preserves the four-agent stability that makes the workflow coherent.
The CLI command surface (`init` / `compose` / `verify`) is intentionally
minimal; npm handles install / remove so the CLI does not duplicate
package manager semantics.

The naming taxonomy classifies skills by nature rather than topic
because mapping every current skill individually showed the topic
buckets mixed natures — a format skill, a language skill, and
practices sharing one domain package. Prefix chains make dependency
edges readable in names: a longer skill name layers on its
prefix-truncated parent and requires it, turning the
guidance-assumption principle into a naming convention. The org layer
splits by artifact type — suffix in skill IDs, prefix in package
names — so generic crafts stay portable while organization workflow
flavor remains a swappable, optional overlay. `domain-*` is redefined
for business domains because no current skill is a business domain;
problem-space packages stay reserved until real domain content
exists.

## Consequences

### Positive

- Conflict detection is a composer property, not a downstream merge
  surprise.
- Capability contracts are stable; OpenCode config changes do not
  require package updates.
- Third parties can publish Roundhouse extensions under their own
  scopes.
- The composer is the single source of truth for "what is installed."
- Skills distribute by nature, so packages no longer mix natures in
  topic buckets; ownership is declared per package, never inferred
  from name prefixes.
- Prefix chains encode dependency edges in names, making installation
  graphs auditable from the manifest without reading skill content.
- Generic crafts stay portable across consumers; org workflow flavor
  is a swappable overlay rather than a fork of the crafts.
- Fission — a skill becoming a base + specialization pair — is a
  normal operation the naming grammar already accommodates.

### Negative

- The composer must implement package discovery, graph construction,
  conflict detection, managed copy, seed creation, composed
  generation, and verification. This is substantial code; the plan
  mitigates by extracting it from `package/deploy-roundhouse.js` and
  testing it against fixtures before operating on real content.
- The normalized model loses fidelity compared to free-form
  OpenCode fragments — for example, packages cannot contribute raw
  `permission` arrays, only canonical allow/deny shapes that the
  composer emits. We accept that loss because the lost
  expressiveness was exactly the part we did not want.
- The taxonomy renames, splits, and folds most current skills; the
  rename map lands with the Phase 5 content migration, and every
  referencing document (the Phase 1 plan's ownership appendix among
  them) must be reworked against the new names.
- The four domain packages dissolve, and `image-media-delivery` is
  retired with its content distributed into future skills, so a
  coverage gap exists until those skills are authored.
- Exact npm naming for org packages is deferred; `backshopdev-*`
  package names are provisional until that discussion lands.

### Follow-up

- Phase 3 builds the composer against fixture packages (no real
  content moved yet).
- Phase 4 refactors Core agent prompts to reason from installed
  skills.
- Phase 5 migrates `src/` content into the new packages.
- Phase 7 exercises a fixture matrix of representative partial
  compositions to confirm the conflict rules behave correctly.
- A future naming discussion pins the exact npm scope and package
  names for org (`backshopdev-*`) packages; this record deliberately
  defers them.
- The skill renames, splits, and folds land with the Phase 5 content
  migration (DEC-20261017-03).
- `DEC-20261017-03`'s Phase 7 composition-matrix entries and
  definition-of-done wording still name the dissolved packages
  (`domain-web`, the documentation package, the spec-workflow
  package, and the contracts package) and must be reworked against
  the nature-based families in the Phase 5 rename wave, alongside
  the skill renames, splits, and folds already tied to Phase 5.

## Assumptions

- A normalized capability model can express every current Roundhouse
  capability.
- The four agent paths the project needs today
  (`orchestrator`, `document-author`, `implementor`, `reviewer`)
  are stable; no fifth agent is anticipated.
- Consumers can tolerate a committed `.roundhouse/manifest.json`
  without treating it as boilerplate.
- Current skills classify by nature into the families above; a skill
  that resists classification is a reconsider trigger, not a
  force-fit.
- Fission is an ordinary maintenance operation: a skill may split
  into a base + specialization pair as understanding matures, and the
  layering grammar absorbs it without a contract change.
- Org practices serve BackShopDev repos beyond Roundhouse, so the
  `backshopdev-*` family is not Roundhouse-specific.

## Reconsider triggers

- OpenCode config shape changes in a way the normalized model cannot
  express (e.g., new top-level keys packages must contribute to).
- A real extension requires contributing capabilities outside the
  `core / workflow / capability / bundle` kinds (e.g., dynamic
  re-configuration of agent prompts). Either extend the contract or
  accept that some extensions cannot be packages.
- A bundle package becomes a real product requirement; the contract
  currently recognizes the `bundle` kind without shipping any
  examples.
- A skill emerges that genuinely cannot classify by nature into any
  family; extend the family set by decision rather than force-fitting
  or reviving topic buckets.
- Org-suffix composition collides with an existing specialization
  chain (for example, a generic base already using the org's name as
  a specialization token); revisit the org-naming rule.
