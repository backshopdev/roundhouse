## Description

The repo's plan/spec lifecycle transitions (Draft → Ready → In progress →
Completed; archival moves; index-row status updates) are enforced only in the
terminal direction — docs-check rejects a terminal-status plan that is not in
`plans/archive/` — but nothing detects the opposite lag: a plan or spec whose
implementation landed (possibly several changesets ago) while its status
stayed "Ready"/"In progress" and its file stayed in the active location. A
docs-check rule could close the gap partially (cross-reference each Ready/In
progress plan against whether its work landed), but the reliable signal is
human/orchestrator attention at changeset close.

## Trigger

The 2026-10-21 docs-hygiene session (PLAN-20261021-03's authoring): the
session caught PLAN-20261019-05 (Phase 7 — composition matrix) still carrying
"Status: Ready" in the active plans index although its implementation had
landed at `03bad7b` four changesets earlier (2026-10-20). The same lag had
hidden the Phase 7+8 completion behind the session-start context's "Phase 7+8
planned but not implemented" framing, which mis-shaped that session's initial
orientation until the drift was discovered.

## Evidence

- PLAN-20261019-05's state before the archival: Status "Ready", unmodified
  since `dd02325` (its creation), active-index row present — while `03bad7b`
  ("test(matrix): add composition matrix; complete Phase 8 sweep",
  2026-10-20) had landed its implementation.
- The session-start context for the 2026-10-21 session carried the stale
  framing ("Phase 7+8 planned but not implemented"), demonstrating the lag's
  downstream cost: orientation begins from a false state.
- docs-check's terminal-archive rule enforces only the terminal direction; a
  grep of the docs-check catalog shows no rule detecting Ready/In-progress
  lag.

## What was tried

The 2026-10-21 session remediated the instance (PLAN-20261019-05 archived
Completed with a dated re-verification note, per PLAN-20261021-03 WP-02
T-03), but no mechanical detection was built — the disposition ruled at Gate
1 was to record the class as this item, not to add a docs-check rule in that
changeset.

## Why this matters now

Every session starts from the repo's committed context; a stale plan/spec
status poisons that context and can mis-direct orientation, planning, and
review. The lag compounds silently: nothing flags it, and the error surfaces
only when a later session happens to look closely. Left open, the class
recurs on every changeset whose close forgets the status advance.

## Resolution criteria

Done when a detection mechanism exists and demonstrably catches the class:
either (a) a docs-check rule that flags any "Ready"/"In progress" plan or
"Active" spec whose described implementation can be shown landed (verifiable
e.g. by commit-message cross-reference) — demonstrated by temporarily
re-introducing a stale status and getting a docs-check failure — or (b) a
standing close-sequence step (checklist item in the commit procedure) that
verifies every changeset's related plans/specs advanced status — captured in
the procedure an executor actually runs, and exercised at the next close.

## Impact

- Severity: Medium
- Affected systems: `docs/plans/*`, `docs/specs/*`, `ktlo/*`, the
  changeset-close discipline, session-start orientation.

## Recurrence

- Frequency: As needed — the class recurs at every changeset close that
  forgets a status advance; the item stays open until a mechanism exists.
- Estimated effort: A docs-check rule (half-day, needs the
  landed-vs-pending signal defined) or a procedure check (minutes, relies on
  discipline).

## Procedure

1. At each changeset close, check whether the changeset completes any plan's
   or spec's implementation; if so, advance the status and archive per the
   terminal patterns.
2. Periodically sweep the active indexes for stale statuses (Ready/In
   progress plans whose work demonstrably landed).
3. When picking up this item, decide between the docs-check rule and the
   procedure step (Resolution criteria's two shapes) and implement it.
