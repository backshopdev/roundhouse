## Description

`scripts/test-commit.js`'s npm-mode-a test sends arguments through the shell
with `cwd: repoRoot` (test-commit.js's `runNpm`, `shell: true`). For the
multi-line-body case, cmd.exe splits the newline-containing argv and the
`--dry-run`/`--dry-run-output` flags are lost — so `scripts/commit.js`
performs a REAL commit in the REAL repo. Demonstrated twice (see Evidence).
The hazard class is transport-level, not case-specific: ANY `test-commit.js`
run while the repo index is non-empty can commit the staged changeset
without approval whenever a shell-transport defect defeats the dry-run
flags — the guard this fix adds is transport-level (skip the runNpm
subtests whenever the index is non-empty or its state is indeterminate),
because no case-level reasoning survives an unknown future transport
defect.

## Trigger

The Phase 4 gate flow's `scripts/test-commit.js` run (2026-10-19): the
npm-mode-a `long-body-with-footers` check lost its `--dry-run` flags to the
shell's newline splitting and committed the real repo's staged changeset.
Recurred 2026-10-21 (see Evidence); the trigger condition is broadened
accordingly: ANY `test-commit.js` run while the repo index is non-empty.

## Evidence

- Commit 7f26922 — the unauthorized commit: mangled message
  ("docs(x): long body — em-dash" / "Body line one — em-dash → arrow."),
  correct content (the 10-file Phase 4 changeset); remediated by the
  human-ruled amend.
- Commit 2c36582 (2026-10-21) — the second demonstration: the
  PLAN-20261021-01 close sequence's test-commit run consumed the entire
  staged 45-file remediation changeset during its close (the failing
  subtest was `npm-mode-a long-body-with-footers`, ENOENT reading the
  never-written dry-run output; the commit content was correct, the
  message mangled; human-ruled amend → `db6be0b`). Same suite result
  33/34, same failing subtest.
- `scripts/test-commit.js`'s `runNpm` — the npm-mode-a invocation runs
  `npm run commit` with `cwd: repoRoot` and `shell: true` (the real repo;
  the temp dir holds only dry-run output files).
- `shellQuote`'s own comment documented the defect's precondition: the
  quoting is "sufficient for the test inputs (subjects/bodies/paths) which
  do not contain newlines" — the long-body case violated the documented
  assumption.
- The suite's header claimed "All cases use --dry-run, so the repository
  is never mutated" — false for the hazardous case (the shell defect
  defeats the flag); both comments are corrected by the fix.

## What was tried

Three fixes were considered (PLAN-20261021-02, Gate 1 rulings
2026-10-21):

1. **Sandbox clone** — rejected as heavy: the suite would run against a
   temporary clone, adding clone/setup machinery and diverging the
   transport under test from the real repo's.
2. **Flag reorder** (placing `--dry-run` ahead of the body argument) —
   REJECTED with the mechanism reason: the newline splits the command
   line into multiple cmd.exe statements, so the trailing body lines
   would still execute as standalone shell commands regardless of flag
   order — the reorder protects only the flags, not the statement
   splitting.
3. **Case drop + startup guard** — the chosen fix: the inline
   multi-line-body npm-mode-a subtest is dropped (it tested a usage the
   house commit procedure forbids — multi-line bodies go via
   `--body-file`; npm-mode-b's `--message-file` case already covers
   multi-line-through-npm via the file transport), and a read-only
   startup guard skips BOTH shell-transport (runNpm) subtest families
   whenever the repo index is non-empty or indeterminate, closing the
   hazard class against any future transport defect.

## Why this matters now

Any future `test-commit.js` run with a non-empty index performs an
unauthorized commit; the harness's approval gates are bypassed by the
shell-splitting defect. The fix removes the hazardous usage and makes the
shell-transport subtests fail-safe against index state.

## Resolution criteria

A `scripts/test-commit.js` run with a non-empty index performs NO real
commit: HEAD and the index are unchanged across the run (recorded before
and after via `git rev-parse HEAD` and a `git ls-files -s` snapshot —
explicitly not `git write-tree`), the runNpm subtests are skipped with
per-test reports and the suite-level guard note, and the run exits 0. The
clean-index run stays green at the recounted 33 checks (34 → 33: the
dropped subtest).

## Resolution

Resolved 2026-10-21. The fix landed in PLAN-20261021-02 (the case drop +
the startup guard; see What was tried item 3). The criterion was
demonstrated at the changeset close, with the changeset's own staged
index as the ruled vehicle: the run classified the index state
`non-empty`, printed the suite-level guard note, skipped all 13
shell-transport (runNpm) subtests with per-test
`SKIP ... (guard: index state non-empty)` reports, ran and passed the 20
direct-mode subtests (20/20, 0 failed, 13 skipped), and exited 0. HEAD
was unchanged across the run
(`8164d73206328c42bb94eac37da0895e3c1a5565` before and after) and the
`git ls-files -s` index snapshot was byte-identical before and after
(same SHA-256; Compare-Object: no differences) — no real commit.
Residual note: npm-transport coverage is exercised in clean-index runs;
the four direct-mode guard tests intentionally omit `--dry-run` and rely
on `scripts/commit.js`'s argument validation, unchanged by this plan.

## Impact

- Severity: High
- Affected systems: `scripts/test-commit.js`, the commit approval gates.

## Recurrence

- Frequency: Every `test-commit.js` run until fixed.
- Estimated effort: One focused harness change (sandbox clone, flag
  reorder, or case drop) plus one verification run.
