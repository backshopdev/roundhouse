# KTLO-20261009-05: Granular installation options

Last modified: 2026-10-09
Status: Active

## Description

<!-- Describe the operational maintenance task, known issue, or recurring
work. -->

Explore making the `init`/`update` lifecycle more granular so consumers
do not have to adopt the full template. The main concern is the skill
set: with 48 skills, consumers may want to install only the skills that
fit their project rather than receiving all of them. Design discussion
is in progress; this item tracks the exploration, the proposed
granularity options, and the eventual decision.

## Impact

<!-- What happens if this item is not addressed? -->

- Severity: Medium
- Affected systems: Template `init` and `update` lifecycle; consumer
  experience; skill allowlists; the sync script if a per-skill filter is
  added.

Affects consumer experience. The current one-size-fits-all install may
not fit all use cases, and forcing every consumer to receive every skill
increases context budget and review surface area for projects that only
need a subset.

## Recurrence

<!-- How often does this work need to be done? -->

- Frequency: As needed
- Estimated effort: Multi-step design work: a decision record, a
  specification, and an implementation plan before any code change.

## Procedure

<!-- Step-by-step instructions for performing this work. -->

1. Survey current consumer use cases and identify the natural axes of
   granularity (skills, agents, hooks, MCP, permissions, etc.).
2. Draft a decision record that names the granularity axes and explains
   the trade-offs of a fully granular install versus the current
   all-or-nothing approach.
3. Write a specification for the chosen granularity model, including
   the `init` and `update` CLI surface and the manifest format used to
   record consumer choices.
4. Write an implementation plan covering the sync script changes,
   manifest migration, and backwards-compatibility expectations.
5. Implement and ship behind the standard SPEC → PLAN → product flow.
