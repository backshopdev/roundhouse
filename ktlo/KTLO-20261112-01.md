## Description

The root `package-lock.json` is now tracked (PLAN-20261112-01 T-12,
ruled at Gate 1 2026-11-12). `@changesets/cli` 3.0.3 has no lockfile
integration: a `changeset version` run rewrites the workspace members'
`package.json` files (version bumps and the CLI's rewritten Core range)
but never the lockfile. The tracked lockfile must therefore be refreshed
(`npm install` at root) after EVERY `changeset version` run — not just
the first — and included in the version commit.

## Trigger

PLAN-20261112-01 (the npm publishing model) ruled the root lockfile
START TRACKING and recorded the maintenance note as its F1 rider. The
note lives in the plan, which moves to `docs/plans/archive/` at close;
this item is the durable operational home for the rule.

## Evidence

- `.changeset/config.json` uses `updateInternalDependencies: "patch"`:
  every Core bump rewrites the CLI's `@backshop/roundhouse-core` range,
  so every version PR desyncs the lockfile from the manifests.
- The plan's post-changeset maintainer flow documents the required
  sequence: `npx changeset version` → `npm install` (REQUIRED: refresh
  the root lockfile) → commit → `npx changeset publish`.
- Without the refresh, the version commit ships a desynced lockfile and
  root `npm ci` fails (install-from-lockfile contradicts the manifests).

## What was tried

N/A — brand-new item, no attempts yet. The rule was ruled at Gate 1
(2026-11-12) and recorded in PLAN-20261112-01 T-12; no version run has
happened since.

## Why this matters now

The first version PR (the maintainer's manual flow) is the next event
that hits this. Skipping the refresh produces a desynced tracked
artifact in the version commit — the exact class of breakage tracking
the lockfile was meant to prevent (reproducible installs for the
workspace). The rule is easy to forget because the changesets tooling
gives no warning.

## Resolution criteria

Every version commit's tree satisfies: `npm install --package-lock-only`
at root after `changeset version` leaves `git diff package-lock.json`
empty (the lockfile already matches the bumped manifests). Equivalently,
`npm ci` at root succeeds on the version commit's tree. The item closes
when the refresh is either automated (a changesets/lockfile integration
or a postversion script) or has survived several version runs as
recorded practice below.

## Impact

- Severity: Medium
- Affected systems: the root workspace lockfile (`package-lock.json`),
  every `changeset version` run and its version commit, root `npm ci`.

## Recurrence

- Frequency: Every `changeset version` run (the accumulate-and-cut
  model: each version PR).
- Estimated effort: one `npm install` at root plus including the
  refreshed lockfile in the version commit.

## Procedure

1. Run `npx changeset version` (the version PR's bump step).
2. Run `npm install` at root — refreshes `package-lock.json` against
   the bumped `package.json` files (and reconciles `node_modules`,
   including the CLI→Core workspace link).
3. Include the refreshed lockfile in the version commit.
4. Verify: `npm ci` at root succeeds (or
   `npm install --package-lock-only` reports no lockfile diff).
