## Description

Two transferable lessons from the PR #4 Copilot review (2026-10-21), recorded
so future check/pipeline designs apply them from the start:

1. **Trace what state each check sees at execution time.** Any pipeline step
   that regenerates state before a check runs can mask the drift the check
   exists to catch. A check's value is determined by the state it observes at
   execution time, not by what it would catch in isolation. Concretely: two
   drift classes must be kept distinct — (a) working-tree drift (a consumer
   hand-edits a composed artifact) and (b) committed-artifact drift (the
   committed artifacts are stale vs the packages). A compose step before a
   verify step makes verify see a freshly rendered, self-consistent tree,
   leaving committed-artifact drift detectable only by a post-compose diff of
   the committed files.
2. **docs-check's link validation does not reach package `managed/` sources.**
   A relative link in a package's `managed/` tree that resolves correctly from
   the package source but escapes the repo root from its composed location
   (`.opencode/`) passes docs-check. Extending link-validation coverage to
   composed-location resolution is follow-up work.

## Trigger

The Copilot review of PR #4 (branch `feature/composable-workflow`), reviewed
2026-10-21, returned five findings; two of them exposed the lessons above:

- F1: `.github/workflows/ci.yml` ran `npm run sync-roundhouse -- --mode sync`
  (compose) before `npm run check-all`, and `check-all` includes
  `check-drift` (the composer's verify). Post-compose verify therefore saw a
  freshly rendered tree and could never catch drift between the COMMITTED
  composed artifacts (`opencode.json`, `.roundhouse/manifest.json`) and what
  the packages would render.
- F4: the four-traversal relative links in
  `packages/roundhouse-core/managed/workflow-docs/autonomy/` (`index.md`
  parent link, `principles.md` AGENTS.md link) were correct from the package
  source but pointed above the repo root from the composed location
  `.opencode/workflow-docs/autonomy/` — and docs-check never flagged them.

## Evidence

- The conflation's origin is traceable in the archived Phase 9 plan's own
  wording: PLAN-20261019-06 (archived) T-10 specified compose-then-verify and
  called it "making the drift check honest (compose-then-verify)" — the
  design conflated the two drift classes into one check's ownership.
- The remediation (PLAN-20261021-01 WP-01) landed `scripts/check-render.js`
  (`git diff --exit-code -- opencode.json .roundhouse/manifest.json`,
  CI-invoked only, clean-tree precondition documented) between compose and
  check-all in `ci.yml`, with the execution-time-state contract line in both
  `AGENTIC_WORKFLOW.md` copies.
- The four-traversal links passed `node .opencode/docs-check.js` on every run
  before the fix; the fix (PLAN-20261021-01 WP-03 T-13) re-pointed both links
  to resolve from the composed location.

## Why this matters now

The masking pattern is reusable: every future CI or local pipeline that
regenerates state before a check runs risks the same vacuity, and the failure
is silent — the check stays green while the invariant it names drifts. The
docs-check coverage gap is live: any package `managed/` link whose
composed-location resolution escapes the repo root lands undetected today.
Leaving this unrecorded means the next pipeline or link change re-learns both
lessons by incident.

## Resolution criteria

1. The execution-time-state lesson is applied at design time: any new check
   added to a pipeline that regenerates state documents (in the check's
   header comment or the workflow contract) what state it sees at execution
   time and which drift class it owns. Verified by review of the next such
   check.
2. docs-check's link validation resolves package `managed/` Markdown links
   from their composed `.opencode/` locations (or an equivalent check exists)
   and flags links escaping the repo root from the composed location.
   Verified by: reintroducing a four-traversal link into a package
   `managed/` tree makes `node .opencode/docs-check.js` exit 1.

## Impact

- Severity: Medium
- Affected systems: CI workflow (`.github/workflows/ci.yml`), the check
  surface (`scripts/check-*.js`), docs-check (`.opencode/docs-check.js`),
  package `managed/` documentation.

## Recurrence

- Frequency: As needed — lesson 1 applies at each new-check design point;
  lesson 2 is a one-time tooling extension.
- Estimated effort: Lesson 1 is a review discipline (minutes per check);
  lesson 2 is a docs-check enhancement (a focused change to the link
  validator plus a fixture-style regression case).

## Procedure

1. When designing or reviewing a check that runs after a state-regenerating
   step, name the state the check sees at execution time and the drift class
   it owns; if a class is left uncovered, add the post-regeneration check
   that covers it (the `check-render` precedent).
2. For lesson 2: extend docs-check's link validation to resolve package
   `managed/` Markdown links from their composed locations; add a regression
   case using the four-traversal shape; run `node .opencode/docs-check.js`
   before and after.
