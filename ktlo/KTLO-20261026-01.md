# KTLO-20261026-01: `.opencode/node_modules/` identified as OpenCode's self-restoring plugin infrastructure (incident record)

Last modified: 2026-10-30
Status: Resolved

## Description

During the `PLAN-20261023-01` implementation session, a large untracked
`node_modules` tree was found under the consumer's managed root at
`.opencode/node_modules/`. The tree is OpenCode's plugin-dependency
infrastructure (identified as such at the 2026-10-29 plan review — ruling
F1; the earlier bare-manual-`npm install`-leftover origin guess is
withdrawn): its three siblings under `.opencode/` are OpenCode-managed
plugin infrastructure — `.opencode/package.json` pins `@opencode-ai/plugin`
(1.19.3), `.opencode/package-lock.json` locks that dependency tree
(including `@opencode-ai/sdk`), and `.opencode/.gitignore` is OpenCode's
generated plugin-dir ignore (it lists `node_modules`, `package.json`,
`package-lock.json`, `bun.lock`, and itself). No plugin is in use today,
so the tree sits dormant — initially read as unused ballast, a framing
recalibrated 2026-10-30: the tree is dormant-but-live OpenCode plugin
infrastructure, not debris; OpenCode's plugin infrastructure needs it
(and restores it — see below).

The mechanism that let it persist: the composer's stale-removal policy
(`SPEC-20261019-02`, SCEN-054) removes only files the composition record
owns; a consumer `.opencode/` file that was never recorded in the manifest
is left untouched. The plugin-dependency tree was never recorded, so the
composer never touched it and it persisted indefinitely by design. **The
policy is correct and unchanged** — a stray tree persisting is the policy
working as designed (protecting genuine consumer files), not a defect in
it. Any composer behavior change is explicitly out of scope (ruled at
Gate 1, 2026-10-26); the verify-warning guard idea was later retired as
unjustified (2026-10-30) — the tree is legitimate infrastructure, and a
warning on it would be noise.

The self-restore discovery (2026-10-30): the pin's mere presence
suffices — OpenCode's startup restores the plugin-dependency tree from
`.opencode/package.json` + its lockfile, with no plugin adoption required
to trigger the restore. Deletion is transient by design: the tree's
presence is the expected steady state, and the restore arrives
automatically at every startup — the retained siblings are exactly the
restoration baseline, with the restore arriving at every startup rather
than on future demand.

Remediation (per `PLAN-20261026-01`): the tree was deleted from the
working tree only — gitignored content (the root `.gitignore`'s
`/.opencode/` rule plus the global `node_modules/` rule), zero git content
in the changeset. Only the tree was deleted; the three
plugin-infrastructure siblings are deliberately retained as the recorded
baseline a future plugin install restores from (human ruling 2026-10-26:
no plugin use now, but near-future adoption cannot be ruled out). The
deletion was performed and verified absent at the time (2026-10-29); the
2026-10-30 restart close restored the tree — the documented result of the
mechanism above, not a failure of the remediation.

## Procedure

1. Confirm no plugin is in use: no plugin member declared in the composed
   `opencode.json`, and no `.opencode/plugins/` directory.
2. If a stale or unwanted dependency tree exists under
   `.opencode/node_modules/`, delete the tree only — never the three
   OpenCode-managed siblings (`.opencode/package.json`,
   `.opencode/package-lock.json`, `.opencode/.gitignore`); the pin and
   lockfile are the recorded baseline a future plugin install restores
   from. Know the deletion is transient: OpenCode's startup restores the
   tree from the retained pin + lockfile, so deletion is point-in-time
   hygiene, not a durable fix.
3. Verify composition health: `npm run sync-roundhouse -- --mode sync`
   (expect no unexpected change — never-recorded paths are invisible to
   the composer), `npm run check-drift`, `npm run check-render`.
4. Restart OpenCode and confirm config, agent, and skill loading (per
   CONTRIBUTING.md's "OpenCode plugin maintenance" update-and-restart
   discipline).
5. Staleness remedy: periodically review the plugin-infrastructure
   territory by hand — the composer's never-recorded policy means such
   trees persist by design, OpenCode's startup restores them even after a
   manual deletion, and if a plugin is adopted, its SDK install belongs
   there. The verify-warning guard idea is retired as unjustified
   (2026-10-30): the tree is legitimate infrastructure, and a warning on
   it would be noise.
