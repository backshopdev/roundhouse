## Correction (added 2026-10-09)

> **Note (legacy framing, preserved below):** The original `Description`, `Impact`, and `Procedure` text below was an on-the-fly conclusion arrived at when the issue surfaced, before the actual mechanism was understood. It attributes the behavior to a model trust boundary on `<system-reminder>` content. **That framing is incorrect** — it is preserved here for the historical record, not as a current characterization.
>
> **Corrected understanding:** OpenCode's AGENTS.md loader (`instruction.ts:210`) delivers colocated `AGENTS.md` content into the Read tool's output as a literal `<system-reminder>…</system-reminder>` block. Cautious models trained to flag prompt injection (correctly) detect this as an in-band instruction block appearing without prior context and ignore it. The observed model behavior in the captured session was sound; the issue is in OpenCode's delivery path, not in the model's trust model.
>
> **Upstream tracking:**
>
> - [anomalyco/opencode#30799](https://github.com/anomalyco/opencode/issues/30799) — primary. Read tool and AGENTS.md loader do not sanitize `<system-reminder>` tags in file content. Closed; assigned to `rekram1-node`; no linked PR.
> - [anomalyco/opencode#19405](https://github.com/anomalyco/opencode/issues/19405) — closest sibling. Same mechanism, opposite leak direction (synthetic reminder lands in user turn). Closed as not planned. A third-party commenter (`dev-paladin`) described an OpenChamber renderer-side stripping workaround and requested a `--no-system-reminder` flag; neither landed.
> - [anomalyco/opencode#30376](https://github.com/anomalyco/opencode/issues/30376) — parent issue. Different vector (read-before-edit enforcement), but shares the `instruction.ts` data structure. Closed.
> - [anomalyco/opencode#26881](https://github.com/anomalyco/opencode/issues/26881) — sibling. Same root class (untrusted content crossing trusted channels), different input channel (VS Code text selection). Closed as not planned.
>
> **All four upstream siblings are closed without a landed PR** (two as `not planned`, two with assignees but no merged fix). Upstream fix is real but uncertain; do not block on it. Local avoidance options (none yet committed) include a one-sentence note in each agent's initial prompt explaining the sidecar delivery.

## Description

<!-- Describe the operational maintenance task, known issue, or recurring
work. -->

MiniMax M3 treats OpenCode's `<system-reminder>` as untrusted content.
Worth investigating model compatibility and whether `AGENTS.md` instructions
are reliably delivered to the model. Determine whether the trust boundary
applied by MiniMax M3 is a model-specific behavior, a class-of-model
behavior, or a more general issue that could affect other models in use.

## Impact

<!-- What happens if this item is not addressed? -->

- Severity: Medium
- Affected systems: Agent runtime; `AGENTS.md` instruction delivery; any
  model that applies a strict trust boundary to system reminders.

If `AGENTS.md` instructions are not reliably delivered to MiniMax M3 (and
potentially other models), workflow behavior could diverge from design
intent. Agents may skip mandatory steps, ignore authority constraints, or
operate outside the documented collaboration model.

## Recurrence

<!-- How often does this work need to be done? -->

- Frequency: As needed
- Estimated effort: Investigation plus a short write-up; one to two sessions.

## Procedure

<!-- Step-by-step instructions for performing this work. -->

1. Confirm the observed behavior: MiniMax M3 treats `<system-reminder>`
   blocks as untrusted user content and may decline or ignore them.
2. Survey the model landscape in use (MiniMax M3 and any others) and
   document which models apply a strict trust boundary to system reminders.
3. Test whether `AGENTS.md` instructions reliably reach the model across
   the surveyed set, including under the trust-boundary behavior.
4. Identify any delivery path that bypasses the trust boundary without
   weakening the prompt-injection defense (e.g., placing critical
   instructions in the initial system message rather than in
   `<system-reminder>`).
5. Record findings in a decision record or specification as appropriate
   and update workflow documentation if a delivery change is warranted.
