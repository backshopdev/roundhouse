## Description

On the maintainer's Windows machine (Windows build 26320, an Insider
build) as of 2026-11-12, NTFS junction *traversal* fails for every
process in the agent-harness session's process tree: stat, readdir,
realpath, and file reads through a junction all fail with
`UNKNOWN: unknown error` (and plain `cmd /c dir` through the junction
reports "File Not Found"). Junction *creation* still works, as does
`lstat` of the link itself. Every operation that traverses a junction —
including the pre-existing `node_modules/@backshop/*` workspace
junctions npm created on 2026-10-19 — is affected.

The repository's junction-dependent surfaces fail as a result:

- The composition-matrix suite
  (`packages/roundhouse-cli/test/composition-matrix.test.js`, hence
  `check-matrix` and the `check-matrix` member of `check-all`): its
  temp consumers junction the real workspace packages into
  `node_modules/`, and the composer's realpath dedupe fails first.
- `npm install` at root: the bin-linking step lstats through the
  junctioned CLI link (`node_modules/@backshop/roundhouse-cli/bin/
  roundhouse.js`) and dies with `UNKNOWN`.
- `scripts/test-sync.js` test 22 and `scripts/test-package.js`'s
  "update ignores unrelated consumer links": both assert
  `fs.existsSync(<junction>)`, which stats the link and gets `UNKNOWN`
  (existsSync → false).

The characteristic signature matches Microsoft's RedirectionGuard /
ProcessRedirectionTrustPolicy mitigation: reparse points are stamped at
creation with the creator's trust level, and a process that enforces
the policy refuses to traverse links stamped untrusted (created by a
non-elevated process). Enforcement is not visible in
`Get-ProcessMitigation -System` (all NOTSET), so the enforcement most
likely lives in the agent-harness host process and is inherited by the
session's children; the maintainer's own console session (outside the
harness) is expected to traverse normally. This is an environment
condition, not a repository defect: the same suite passed on this
machine in October 2026 (the npm junctions date from then), and CI
(Linux) uses real symlinks whose realpath works.

## Trigger

2026-11-12, during PLAN-20261112-01's WP-07 verification battery: the
composition-matrix suite — green at its 2026-10 landing — failed all 10
tests with `Error: cannot resolve candidate package root ... UNKNOWN:
unknown error, stat '...\node_modules\@backshop\roundhouse-core'`. A
minimal probe (fresh temp dir, junction created via both
`fs.symlinkSync(..., "junction")` and elevated-tag-neutral
`mklink /J`) reproduced the failure with plain `fs.statSync`,
`fs.realpathSync`, `fs.readdirSync`, and read-through opens; the repo's
own pre-existing npm junctions failed identically; `npm install` at
root failed in the bin-linking step with the same `UNKNOWN` lstat.

## Evidence

- Minimal probe (fresh junction to an existing directory):
  `realpath FAIL UNKNOWN`, `stat FAIL UNKNOWN`, `readdir FAIL UNKNOWN`,
  read-through `open FAIL UNKNOWN`; `mklink /J`-created junction:
  identical; directory-symlink creation: `EPERM` (no symlink privilege).
- Repo junctions: `dir /a node_modules\@backshop` lists the 33
  `<JUNCTION>` entries with targets; traversal (`dir /b
  node_modules\@backshop\roundhouse-cli`) → "File Not Found".
- `npm install` at root: `npm error UNKNOWN ... lstat
  '...\node_modules\@backshop\roundhouse-cli\bin\roundhouse.js'`.
- `npm install --package-lock-only` at root SUCCEEDS (no node_modules
  work, no bin linking) — the viable lockfile path in this state.
- Unaffected (no junction traversal needed): the composer suite
  (directory copies), SCEN-059's real-root discovery,
  check-contracts/check-deps/check-drift/check-pack/check-render,
  test-sync (except test 22's existsSync assert), test-commit.
- RedirectionGuard mechanism reference: Windows 11's
  ProcessRedirectionTrustPolicy — reparse points stamped with the
  creator's trust level at creation; enforcing processes refuse
  untrusted (non-elevated-created) links.

## What was tried

- Creating junctions via `fs.symlinkSync(..., "junction")` and via
  `mklink /J`: both creation paths succeed; both fail to traverse.
- Traversal from Node and from `cmd /c dir` through both fresh and
  pre-existing junctions: all fail (the block is not Node-specific and
  not specific to newly created links).
- `Get-ProcessMitigation -System`: no RedirectionTrust policy visible
  (all NOTSET) — the enforcement is not a system-wide default, so it is
  most plausibly inherited from the agent-harness host process.
- No attempt was made to evade or disable the mitigation: it is a
  Windows security mitigation against junction redirection attacks, and
  the harness's universal rules forbid wrappers that evade security
  boundaries. Recreating the junctions from an elevated process (which
  would stamp them trusted) is the legitimate remedy and requires the
  maintainer.

## Why this matters now

The local check battery on this machine is partially dead: `check-all`
cannot go green (its `check-matrix` member cannot run), and root
`npm install` fails — which also blocks the KTLO-20261112-01 refresh
step's full form (only `--package-lock-only` works here). If the
maintainer treats the local failures as repository regressions, real
work stalls; if they go unnoticed, the junction-dependent surfaces
(matrix suite, npm bin linking) lose their local verification. The
condition also risks misdiagnosis as a composer bug (the failure
surfaces inside the composer's realpath dedupe).

## Resolution criteria

The composition-matrix suite passes end to end on this machine — either
run from a process tree that traverses junctions (the maintainer's own
console session), after the workspace junctions are recreated by an
elevated process (trusted-stamped), or on a Windows build/policy state
where traversal is no longer blocked. The concrete check:
`npm run check-matrix` exits 0 locally, and `npm install` at root
completes without an `UNKNOWN` lstat error. Record the outcome in the
History table; close the item when the passing condition is confirmed
and stable.

## Impact

- Severity: Medium (local development/verification on one machine; CI
  and other environments unaffected)
- Affected systems: `check-matrix` / `check-all` (matrix member), the
  composition-matrix suite, root `npm install` (bin linking),
  test-sync test 22 and test-package's unrelated-link assert.

## Recurrence

- Frequency: Every local battery run in an affected session, until
  resolved.
- Estimated effort: one manual verification run from the maintainer's
  console (or elevated junction recreation, one-time).

## Procedure

1. From the maintainer's own console (outside the agent harness), run
   `npm run check-matrix`. If it passes, the block is harness-process-
   scoped; record that in History and treat harness-session matrix
   failures as environmental noise (with the
   KTLO-20261112-01 caveat that root `npm install` must then also run
   from the console).
2. If it still fails from the console, recreate the workspace links
   from an elevated prompt (`rmdir node_modules\@backshop\<member>` +
   `mklink /J ...`, or a fresh `npm install` from the elevated prompt)
   so the junctions carry trusted stamps, then re-run.
3. If it still fails, the block is machine-wide: check for a Windows
   update or new mitigation policy on this Insider build, and fall back
   to CI as the junction-dependent surfaces' verification venue.
4. Update this item's History with the observed outcome and close when
   the Resolution criteria hold.
